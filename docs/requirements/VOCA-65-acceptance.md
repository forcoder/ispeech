## 1. 条目一：快捷短语搜索框中间编辑

### 1.1 用户场景与目标

用户在快捷短语面板里搜一个长词（原文举例「用的请自行清理干净，放回原位！蟑螂」），发现中间打错一个字，只能从末尾一路退格删到那个字再重打。

**一句话目标**：让用户在不重输的前提下改搜索词的任意位置。**不做会怎样**：长词搜索的编辑成本约等于重输，用户改回用主输入框打字，面板的搜索能力被浪费。

### 1.2 现状（代码证据，不重新论证）

| 事实 | 位置 |
|---|---|
| 搜索框右侧已有 ✕，点击清空全部并重新聚焦 | `QuickPhrasePanel.kt:701-714`、服务侧 `IspeechImeService.kt:333` |
| 搜索词是服务侧一个 `String panelKeyword`，**只有整体替换，没有光标位置** | `IspeechImeService.kt:195`、`1343-1348` |
| 所有输入都是「追加到末尾」：软键盘字母、候选上屏、直接上屏、硬件键盘字母 | `IspeechImeService.kt:553`、`926`、`951`、`1344` |
| 退格只删末尾一个字符 | `IspeechImeService.kt:1350-1353` |
| 光标是一个自绘 `View`，插在文本后面固定位置，不随内容移动 | `QuickPhrasePanel.kt:691-694`、`render()` 恒 `setSelection(length)` |

**结论**：用户说的「没有清空按钮」与代码不符（可能是旧版 APK，见 §9 假设 A1）；真正的缺口是**没有光标位置这个概念**，因此无法中间插入/中间删除。

### 1.3 范围

**做**：光标左移 / 右移；在光标处插入字符；在光标处删除字符（删除光标前一个）；保留 ✕ 一键清空。

**不做**：
- 「新输入自动清空原有内容」（方案 ②）——不在本批，见 §7 Q1。
- 文字选区 / 复制 / 粘贴（新的编辑能力，需单独 issue）。
- 让搜索框弹出系统键盘（现有设计明确「不抢焦点」，见 `QuickPhrasePanel.kt:678-689` 注释；本批不推翻）。

### 1.4 可测验收标准

判定方式：`JVM` = 纯函数单测（无 Android 依赖）；`adb` = 真机/模拟器操作后读输入框文本或 `dumpsys`。

| ID | Given | When | Then | 判定 |
|---|---|---|---|---|
| AC-1.1 | 关键词「abcd」，光标在索引 2 | 插入「X」 | 结果「abXcd」，光标索引 3 | JVM |

**异常态覆盖**：空输入（AC-1.5）、组合中（AC-1.7）、超长文本（AC-1.8）、重复打开（AC-1.10）。

#### 四条 AC 的口径定义（v1.1 修订：AC-1.9 语义修订 R1；AC-1.7/1.8/1.10 补定义 C2/C1/C3）

**AC-1.9（R1 语义修订）** 原写「连续输入 3 个字母 → 插入光标处」在**中文态不成立**：中文态字母走 `handleChar()` 的 `buffer += lower`（`IspeechImeService.kt:655-675`），进的是编码缓冲，不会立刻写进搜索词，按原文测中文态必然判失败。修订后只对「直接产生字符」的路径成立：

- 计入的路径：英文态字母键、硬件键盘字母（`buffer` 为空时）、候选上屏、数字/符号键直出、emoji。
- **不计入**：中文态字母（进编码缓冲）、九宫格数字串（进 `t9Digits`）。这类情况下**光标不动**，等候选上屏时才按「整段插入光标处、光标后移该文本码点数」生效（交互规格 R1-11/R1-24）。
- 断言：`("abcd", 2)` + 依次产生 `X` `Y` `Z` → `"abXYZcd"`，光标 5；末尾 `cd` 不截断。

**AC-1.7（C2 补定义）** 「组合中」= 编码缓冲 `buffer.isNotEmpty()` **或** 九宫格数字串 `t9Digits.isNotEmpty()`。软键盘与硬件键盘一致（硬件分支 `KEYCODE_DEL` 现走 `backspacePanelKeyword()`，见 `IspeechImeService.kt:539-542`，需对齐为「先删编码」）。判定点：退格后 `panelKeyword` 与 `cursor` 均不变。

**AC-1.8（C1 补定义）** 20 字是**种子**上限（`PANEL_SEED_MAX_CHARS`，`IspeechImeService.kt:107`、`:1226` 只用于取宿主光标前 20 码点作种子），**编辑不设硬上限**：达到 20 字后继续输入/选候选一律允许，不做静默拒绝、不弹提示。本条判定点是布局与可点性——✕ 不被文本覆盖、✕ 可点 ≥40×40 dp、光标完整可见；不要求「拒绝第 21 个字符」。

**AC-1.10（C3 补定义）** 复位触发补全为四类：① 收起面板再打开；② 切面板（如剪贴板）再切回；③ 旋转屏重建；④ 宿主输入框切换。一律光标回末尾，不恢复中间位置。

### 1.5 成功度量

「搜索框退格次数 / 每次搜索」——当前无埋点，**基线待补测**；采集方式：在 `panelKeyword` 的退格分支加计数并落到 `input_stats.txt` 的扩展字段。目标值待基线出来后定，**本项不作为验收门禁**。

### 1.6 下一步 owner 建议

**UX**（必选）：需要产出「光标怎么移动」的交互规格——键盘上已无方向键（`KeyAction.MOVE_LEFT/MOVE_RIGHT` 在 `KeyboardLayouts` 与 `T9Layouts` 里 0 处使用，只有服务侧有分支），且面板态下硬件方向键被放行给宿主应用（`IspeechImeService.kt:561-566` 在 buffer 为空时返回 `false`），所以「怎么移动光标」是必须由 UX 定的新交互，见 §7 Q1-b。
输入：本文 AC-1.1~1.10 + §7 Q1 的人类结论。

## 2. 条目二：字母键浮层（大小写 + 右上角角标）

### 2.1 用户场景与目标

字母键右上角印着小字（q 上是 1、a 上是 ~、z 上是 ( ），但点按只出字母，想打那个角标字符只能翻符号页；想打大写要先按 Shift。

**一句话目标**：一次长按拿到「该字母大小写 + 该键角标字符」。**不做会怎样**：角标字符是纯装饰，用户为了打 `(`、`~`、`#` 要切两次页面。

### 2.2 现状（代码证据）

| 事实 | 位置 |
|---|---|
| 字母键由 `letterKeys()` 生成：`output` 小写、`label` 大写、`hint` 取字符串对应位 | `KeyboardLayouts.kt:27-38` |
| 26 键的 hint 表：`qwertyuiop→1234567890`、`asdfghjkl→~!@#%""*?`、`zxcvbnm→()-—:;` | `KeyboardLayouts.kt:125-128` |
| 字母键的 `alt` 为空列表 → 没有长按浮层 | `KeyDef.char()` 默认 `alt = emptyList()`（`KeyDef.kt:160`） |
| 长按浮层只对 `alt` 非空的键生效（数字 / 标点 / 逗号句号） | `SoftKeyboardView.kt:590-596` |
| 浮层实现：`PopupWindow` + 横向条，每项 40×40 dp，点击后 `onKey(KeyDef.char(alt))` | `SoftKeyboardView.kt:832-877` |

**两个必须一起解决的现状缺陷**（否则浮层做出来也是错的）：

1. **`zxcvbnm` 只有 6 个 hint**（7 个字母）：`m` 的角标为空。浮层对 m 只能给 `m/M`。
2. **浮层选中的字符若走 `KeyAction.CHAR`，在中文态会进编码缓冲**：`handleChar()` 里 `mode != ENGLISH && !upper` 时一律 `buffer += lower`（`IspeechImeService.kt:655-675`）。也就是说，选「A」会变成往输入缓冲塞一个 `a`，而不是上屏 `A`。验收标准必须把这条钉死。

### 2.3 范围

**做**：长按字母键 → 浮层展示 `[小写, 大写, 角标字符]`（角标为空则只有前两项）；点选后**原样上屏**。

**不做**：
- 不改点按行为（点按仍是输入字母）。
- 不发明角标表以外的新字符（不自行扩展字符集）。
- 不做滑动选字（搜狗式 finger-slide 选择），本批只做点选。

### 2.4 可测验收标准

| ID | Given | When | Then | 判定 |
|---|---|---|---|---|
| AC-2.1 | 中文态字母页 | 长按 q 至系统长按阈值（`ViewConfiguration` 默认 500 ms）后再抬起 | 浮层出现，含 3 项 `q` `Q` `1` | adb |
| AC-2.2 | 同上 | 点 `1` | 宿主输入框出现「1」；输入法窗口不关闭、不跳页 | adb |
| AC-2.3 | 中文态字母页，**中文标点开启 + 全角输出开启**（最严组合） | 长按 a → 点 `~` | 上屏「~」，**不被中文标点转换成「～」、也不被全角输出转换成「～」**（见下方口径） | adb |
| AC-2.4 | 中文态字母页 | 长按 a → 点 `A` | 上屏「A」，**编码缓冲为空**（随即输入 `wqiy` 应查「你」而不是把 A 混进码）；**若长按前编码缓冲非空，先按现有规则上屏该编码，再上屏「A」** | adb |
| AC-2.5 | 英文态字母页 | 长按 q → 点 `Q` | 上屏「Q」，且 Shift 状态不被改变 | adb |

| AC-2.7 | 任一字母键 | 生成浮层条目 | 顺序为 `[小写, 大写, hint]`，重复项去重（hint 与小写相同时只 2 项），条目数 ∈ {2,3} | JVM |
| AC-2.8 | 26 个字母键 | 生成本页浮层数据 | 每个键的 hint 为空或**恰好 1 个字符**；`m` 键要么补角标、要么明确为空（**现状 7 字母 6 角标，需修正**） | JVM |
| AC-2.9 | 中文态字母页 | 连按 q 三次，每击按压时长 ≤ 100 ms、间隔 ≤ 100 ms | 上屏「qqq」，全程不弹浮层（三次都是短按） | adb |
| AC-2.10 | 浮层已弹出 | **任一清理触发**：切面板 / 收键盘 / 旋转 / 宿主切换 / 窗口失焦 / 视图销毁 | 浮层随窗口消失，无残留 `PopupWindow`（`dumpsys window` 无游离窗口） | adb |

**异常态覆盖**：快速连按（AC-2.9）、中断（AC-2.10）、无角标键（AC-2.7/2.8）、空缓冲（AC-2.4）。

#### AC-2.3 / AC-2.4 / AC-2.6 / AC-2.10 的口径（v1.1 修订：R2、R3 语义修订；C4、C5 补定义）

**AC-2.3（R2 语义修订）** 原文只挡了「中文标点转换」，漏了**全角输出**。证据：浮层回调若走 `commitDirect`，进入 `commitDirect(applyFullWidth(raw), …)`（`IspeechImeService.kt:651`、`:664`），`applyFullWidth` 在 `settings.fullWidth` 为真时把可打印 ASCII 全部 `+0xFEE0`（`Punctuation.kt:55-66`，`:975` 调用），`~` 会变成「～」、`1` 变成「１」。修订后：**浮层的选中项是「精确取字符」，原样上屏——既不经 `PunctuationConverter` 的中文标点映射，也不经 `applyFullWidth` 的全角转换**。验收要在「中文标点开 + 全角开」的组合下测一次（点 `~` 出 `~`、点 `1` 出 `1`），只在「全角关」下测不算通过。

**AC-2.4（R3 语义修订）** 原文只定义了「缓冲为空」的情形，未定义**长按前缓冲非空**时怎么办。现状约定是「直出字符前先 `commitTop()`」（`IspeechImeService.kt:649-651`：非字母字符上屏前若 `buffer` 非空先上屏未完成编码）。浮层选字必须沿用同一约定：**若长按前编码缓冲非空，先按现有规则把该编码上屏（等价 `commitTop()`），再上屏所选字符**；不得静默丢弃用户已输入的编码（那是数据丢失，用户会认为「我打的码被吃了」）。判定点：① 缓冲为空时选 `A` → 上屏「A」、缓冲仍空、随后 `wqiy` 查「你」；② 缓冲为「ni」时选 `A` → 先上屏「ni」对应的结果、再上屏「A」、缓冲清空。

**AC-2.6（C4 补定义）** 两条退回路径的行为不同，分开验：
- **按返回**：只关闭浮层并**消费该返回键**（不把 BACK 传给宿主 App），**快捷短语面板不关**。
- **点浮层外**：只关闭浮层，**该次点击不穿透**到浮层下面被覆盖的键（不能因为关浮层顺手打出一个字符）。

**AC-2.10（C5 补定义）** 清理触发补全为六类：切面板、收起键盘、旋转、宿主切换、输入法窗口失焦、视图销毁（`onDestroy` / detach）。判据统一为「`dumpsys window` 无游离 `PopupWindow`」，不逐类写不同判据。

### 2.5 成功度量

「角标字符上屏次数 / 26 键字母上屏次数」——无埋点，**基线待补测**。本项不作验收门禁。

### 2.6 下一步 owner 建议

**UX**（必选）：触发方式与浮层层级（是否遮挡候选条）。**UI**：浮层外观需沿用键面设计令牌，不得新造魔法值。

## 3. 条目三：词组自学习（手动拼接）

### 3.1 用户场景与目标

用户要打一个词库里没有的词（如「喂猫」），只能先打 `klge` 选「喂」、再打 `qtal` 选「猫」；下次打同一个词，还得重复一遍。

**一句话目标**：把「用户连续拼出来的两个字」记成词组，下次打对应的码就能直接选。**不做会怎样**：长尾新词（网络用语、昵称、方言词）永远靠逐字拼，这正是五笔用户最费力的场景。这是本批**用户价值最高**的一条。

### 3.3 我在基线上做的数据核对（本轮新增证据）

词组编码不能靠猜。我把内置 `wubi86.dict`（165,599 行）按五笔词组规则全量回算了一遍：

| 词长 | 条数 | 按规则回算一致 | 不一致 | 一致率 |
|---|---:|---:|---:|---:|
| 2 字（首2+首2） | 66,534 | 66,413 | 119 | **99.82%** |
| 3 字（首1+首1+末2） | 11,295 | 11,287 | 6 | **99.93%** |
| 4 字（首1×4） | 11,618 | 11,616 | 1 | 99.99% |
| 5 字（首1×3+末1） | 706 | 706 | 0 | 100% |

- 不一致的 119 条集中在同部首字（`蹒跚` 实际码 `kakm`，按规则算 `khkh`），属词库自身的简码约定，不是规则错。
- 结论：**五笔 2 字词组的编码可由两个字的全码确定性推导**，可靠到可以直接写进验收标准。
- 复现方式：解析 `app/src/main/assets/wubi86.dict` 前 3 列，单字取「4 码且权重最高」那条全码，按上表规则拼接后与行内 code 比对。

**拼音没有这个性质**：拼音词组码要反查两个字各自的读音，多音字有歧义（`猫` 在 `pinyin86.dict` 里同时有 `mao` / `miao`），且用户词库会把音节间空格过滤掉（`UserDictStore.kt:95-98`），推导链更长、更脆。这是 §7 Q3-3 建议「一期只做五笔」的直接依据。

#### AC-3.4 判定口径（v1.1 修订，原标 `JVM` → `JVM + 真机`）

原标「JVM」不成立：「切面板」这一半是纯状态机事件，可以用纯函数断言；「移动光标」这一半**在现状代码里没有事件源**——`IspeechImeService` 全仓 0 处覆写 `onUpdateSelection`（`grep -rn onUpdateSelection app/src` 无命中），只能新增覆写才能拿到通知，而该回调的时序与自因/他因区分依 ROM 而异。因此拆成两层，两层都必须过：

| 层 | 验什么 | 具体断言（可执行路径） | 通过判据 |
|---|---|---|---|
| **JVM（纯函数层）** | 语义：中断后不写库 | ① `interruptByPanel`：`onCommit("喂",SINGLE_CHAR,t0)` → `onInterrupt()`（`openPanel`/`closePanel` 两处各一条）→ `onCommit("猫",SINGLE_CHAR,t0+1.9s)` → tracker 返回「不写库」，单元测试断言写入次数 0、状态回 `idle`。② `resetOnInputChange`：`onCommit` → `reset()`（`toggleMode`/`onStartInput`）→ `onCommit` → 0 次写入。③ **自因过滤的纯逻辑单测**：把「是否自因」抽成纯函数 `isSelfCausedSelectionChange(newSelStart, lastCommittedCursor, tolerance)`，用表驱动断言——`newSelStart == lastCommittedCursor` → 自因（不中断）；`diff > tolerance` → 他因（中断）；同一 commit 的重复回调 → 自因。④ 降级分支也要有用例：`tolerance = 0`（只比 `newSelStart`）时上述表的行为符合预期 | 全部单测通过，且 ③ 覆盖「自因不误中断 / 他因必中断」两类 |
| **真机（ROM 时序层）** | `onUpdateSelection` 在真实 IME 会话里的回调顺序与自因过滤是否有效 | 参考机型上开 `logcat` 抓 `phrase_learn` 结构化日志，跑三组：① 连续拼两个单字（不移动光标）→ 期望日志出现 `phrase_learn commit{...}` 且**无** `skipped{reason=interrupt}`，词库实际新增 1 条；② 拼完第一字后用系统手势/方向键把宿主光标移开 → 期望出现 `skipped{reason=interrupt}`，词库**无**新增；③ 拼第一字后切短语面板再切回 → 期望同上，无新增 | 三组结果全部符合；且 ① 组连续 10 次无一次误中断（否则 `F1` 成立，按 ADR 降级并补记录） |

**为什么不用「JVM 足够」的写法**：AC-3.4 的语义是「用户移动光标时不学」，而 JVM 层拿不到「用户移动了光标」这个事实——只能测我喂进去的 `onInterrupt()`。只写 JVM 等于用 mock 测自己的 mock，无法证明真实链路会触发中断。真机层这一组断言（尤其是 ① 的反向用例：**正常上屏不能被自己误判为中断**）才是这条 AC 的真实风险点。

**真机组的取证要求**（供测试执行）：机型 / ROM 版本 / `logcat` 关键行原文随测试报告留档；不可只写「已验」。ADR §8 T-3 与本表是同一件事，两处结论必须一致。

## 4. 条目四：按键触控热区与方块键尺寸

### 4.1 用户场景与目标

用户反馈「多次点击按键会出现点了没反应、定位偏移」，并希望按键接近搜狗白色方块键、触控范围与方框对齐。

**一句话目标**：手指落在键面方框内的任何位置都必须触发该键。**不做会怎样**：每次输入都随机丢键，这是**功能缺陷**级别的问题，不只是观感。

### 4.2 现状（代码证据 + 估算）

| 事实 | 位置 |
|---|---|
| 每个键四周各 4 dp `margin` → 相邻键之间有 8 dp 不可点区域 | `SoftKeyboardView.kt:119`、`485`、`521`、`539` |
| 键高默认 52 dp，字号 23 sp，圆角 10 dp | `SoftKeyboardView.kt:967`、`407-413`、`120` |
| 全仓**没有任何** `TouchDelegate` / `dispatchTouchEvent` 重写 → 死区里的触摸落到底层 `LinearLayout`，无人处理 | 全仓 0 命中 |
| 行首尾另有 3 dp padding | `SoftKeyboardView.kt:239` |
| 参照：搜狗同机实测字母键宽 120 px（36.9 dp）、键间距 6 px | `docs/keyboard-ui.md` §2 |

**死区面积估算**（按本机 1260 px / 3.25 = 387.7 dp 宽、10 列、行内 3 dp padding、键高 52 dp 计算）：

| keyMargin | 单键可点面积占键格比 | 死区占比 |
|---|---:|---:|
| 4 dp（现状） | 68.5% | **31.5%** |
| 3 dp（VOCA-30 目标态） | 75.6% | 24.4% |

> 这是**按布局参数算的模型值，不是真机实测**（本机无 `adb`，见 §9）。真机复测在 M3 做。

> **40 dp 触控规范对 26 键字母键不适用（本轮修正）**：387.7 dp 屏宽扣掉行内 3 dp 左右 padding 后
> 每格只有 **38.17 dp**（(387.69−6)/10），字母键**在物理上不可能达到 40 dp 宽**
> （搜狗同屏实测键宽 36.9 dp，同样不达标）。
> 因此 AC-4.6 对字母键按「**可点宽 = 键格宽 ≥ 38 dp**」验收（不是键面 32.17 dp，也不是「填满键格」的
> 相对口径——参考机型上二者数值一致，但口径必须是绝对值，否则窄屏会滑向 31.4 dp）；
> 窄屏与底行 1.0 权重键改按「填满键格」；40 dp 下限只对功能键 / 工具栏键 / 搜索框 ✕ 这类独立控件生效。
> 若不这样拆，验收时会用一个达不到的数字卡住实现。详见 §4.5 的 R4 口径表。

**注意**：「定位偏移」（点 A 出 B）用 margin 解释不了——margin 只会造成「无响应」，不会造成「打到隔壁」。这条需要人类补复现视频才能定根因，见 §7 Q4-b。

### 4.3 与在审改动的去重结论（关键）

| 已在别处覆盖 | 出处 | 本批是否重复做 |
|---|---|---|
| 字母字号 23 → 18 sp、键间距 8 → 6 px、圆角 10 → 6 dp、换行键重设计、底行权重 | VOCA-30（`in_review`，`docs/keyboard-ui.md`） | **不做** |
| 候选词不加粗 | VOCA-56（`in_review`） | **不做** |
| 键高默认 52 → 46 dp、候选条改单行、双击空格、滑动翻页、按键音效 | VOCA-45 规格 → VOCA-46（`backlog`） | **不做**（含「整体缩小按键高度」这条，用户的诉求已被 VOCA-45/46 吸收） |

**本批真正剩下的只有三件**：① 可点区域消死区（hit = 键格，不是键面）；② 方块键的宽高比例（在 46 dp 键高基准下仍是方块）；③ 独立控件（功能键 / 工具栏 / 面板按钮）的最小可点 ≥ 40 dp 兜底 —— 26 键字母键受屏宽限制按「可点宽 ≥ 38 dp」验收，见 §4.2 注。

### 4.4 范围

**做**：可点热区 = 键格（覆盖键面 + 相邻间隙各半，键间 0 空洞）；方块键比例；字母键可点宽 ≥ 38 dp、可点高 ≥ 40 dp；功能键与独立控件 ≥ 40×40 dp（窄屏与底行 1.0 权重键按「填满键格」）；改造后键盘总高相对合并后基线变化 ≤ 8 dp。

**不做**：任何字号 / 字重 / 配色 / 圆角 / 键高默认值 / 候选条结构 / 底行权重的改动（全部归上述三个 issue）。

#### AC-4.1 / 4.3 / 4.4 / 4.6 的口径（v1.1 修订：R4、R5 语义修订；C6、C7 补定义）

先统一三个矩形，后文全部按此口径量，避免验收时量错对象：

| 名称 | 定义 | VOCA-30 + VOCA-46 合并后参考值（参考机型 387.69 dp 宽） |
|---|---|---|
| **键格 cell** | 布局分配得到的格子 = 键面 + 相邻 margin 各一半 | 字母键 38.169 × 52 dp |
| **键面 face** | 用户看到的白色方块 | 字母键 32.169 × 46 dp |
| **可点 hit** | 实际参与命中的矩形，**= 键格** | 字母键 38.169 × 52 dp |

**AC-4.3（R5 语义修订）** 原文「可点矩形与**视觉外框**误差 ≤ 1 dp」里的「视觉外框」有歧义：若理解为白色键面（32.169 dp），就与 AC-4.6 的「≥ 38 dp」相差 6 dp，两条 AC 在字面上无法同时满足（v1.1 已消除）。修订后定义唯一：「视觉外框」在本条里指**键格边界**（键面 + 相邻间隙各半），不是键面。判定：`|hit.left − cell.left| ≤ 1 dp` 等四边逐条成立，用**同一个 layout pass** 的结果计算（不得用上一帧或被 margin 修正过的旧值）；相邻 hit 之间 0 空洞（不重叠、不留缝）。行首尾 3 dp padding 不在键格内，也不计入「空洞」。

**AC-4.6（R4 语义修订）** 原文「字母键宽 ≥ 38 dp、功能键/工具栏/搜索框 ✕ ≥ 40×40 dp」有三处按字面不可执行，逐项改：

| 对象 | 原文问题 | v1.1 口径 |
|---|---|---|
| 字母键（宽） | 「键宽」若量白色键面（32.169 dp）则**任何实现都不达标** | 按**可点宽**量 = 键格 38.169 dp ≥ 38 dp。键面宽不参与本条判定 |
| 字母键（高） | 未区分键格与键面 | 按可点高量 = 键格 52 dp ≥ 40 dp（现状即达标；`MIN_KEY_HEIGHT_DP = 40` 是约束键面高的常量，`SoftKeyboardView.kt:968`） |
| 窄屏（如 320 dp 宽） | 320 dp 屏 10 等分后键格仅 **31.4 dp**，≥38 dp 物理不可达 | 按「**填满键格**」验收：hit 宽 = cell 宽（误差 ≤1 dp），不再要求绝对 dp 数 |
| 底行 1.0 权重键（`符` / `123` / `，` / `。`） | 键格 **33.78～35.16 dp**（见下），≥40 dp 物理不可达 | 同按「填满键格」验收 |
| 独立控件（工具栏键、搜索框 `✕`、面板按钮） | 现状工具栏高 34 dp、`✕` 30×28 dp，均不达标 | 仍要求 **≥40×40 dp**；工具栏 34 → 40 的高度调整归 VOCA-46（见 §4.3、交互规格 §7 C-1） |

底行键格宽的可复现算法（不写死数字，量的时候按当时权重算）：

```
cell(weight w) = (屏宽 − 2×行内padding − 7×键间距) / Σweight × w + 键间距
参考机型：387.69 − 6 − 42 = 339.69；VOCA-30 权重 Σ = 1.6+1.5+1+3.3+1+1.45+1.8 = 11.65
  → 1.0 权重键 cell = 339.69/11.65 + 6 = 35.16 dp（< 40，故按「填满键格」验收）
若把 Σ 简化成 11.3（不计 margin 的口径）则得 33.78 dp —— 两个数都小于 40，结论不变。
```

**AC-4.1（C6 补定义）** 命中判定 = 「点落在哪个键格」：**水平中线归左、垂直中线归上、四键交汇的十字中心归左上**；边界点浮点相等时按「行优先、列优先」取第一个包含该点的键，结果确定可复现。行首尾 padding 不在判定范围（点在那里不命中任何键，属屏边误触保护，不计入「键间空洞」）。

**AC-4.4（C7 补定义）** **武装区** = 被按下键的 hit 矩形 ∪ 该键预览气泡矩形，再向外留 4 dp 迟滞。手指滑入气泡范围**仍属武装区**，不取消、原键照常生效；**滑出武装区超过 4 dp 才作废**（清按下态、收气泡、停长按计时器）；作废后**滑回可恢复**；**其他键在任何情况下都不得被按下或上屏**（按下键粘滞，避免「点 A 出 B」的观感）。

### 4.6 成功度量

「每次会话的丢键率」——**无法采集**（现无输入级埋点，`InputStats` 只记上屏次数，取不到「点了没出字」）。标注 **待补测**，采集方式：真机脚本按固定点位点击并比对输入框文本（AC-4.2 就是这个脚本的雏形）。本项不作验收门禁，AC-4.2 的 130/130 是门禁。

### 4.7 下一步 owner 建议

**UX**（已定，v1.1）：间隙点击的命中规则见 AC-4.1 口径（C6）——「点落在哪个键格就命中哪个键」，水平中线归左、垂直中线归上、十字中心归左上。原 §7 Q4-c 的两个候选（最近中心 vs 偏向下一个键）均不采用。

## 7. 决策记录（13 项，2026-11-13 全部按推荐值落定）

### Q1 第 1 条：清空方案选 ① 还是 ②？

- **选项 A（推荐）**：只做「光标定位 + 中间编辑」，保留现有 ✕。②「新输入自动清空」不做。
  理由：✕ 已提供一键清空（一次点击的成本已经很低）；② 会在用户想「在原词上接着打」时误删已有内容，且没有撤销。
- **选项 B**：A + 「新输入自动清空」做成设置项（默认关）。
  代价：多一个设置项 + 多一条状态：何时算「新输入」（打开面板后的第一个字符？还是光标在末尾的第一个字符？），歧义面大。

**推荐 A。** 若人类坚持 B，请一并回答：自动清空的触发点是什么。

### Q1-b 第 1 条：光标怎么移动？（UX 必答，影响 AC-1.3/1.4 的可操作性）

- **选项 A（推荐）**：面板内自带一对「◀ ▶」小键（放在搜索框右侧、✕ 左边）。
  理由：面板态下键盘已无方向键，硬件方向键被放行给宿主应用（`IspeechImeService.kt:561-566`），不加键就没有移动手段。
- **选项 B**：直接点搜索框文字位置定位光标。
  代价：搜索框刻意不持有 Android 焦点（`QuickPhrasePanel.kt:678-689` 明确写了抢焦点会导致跳页 / 按键被吞），点按定位要推翻这个设计，回归风险高。

**推荐 A。**

### Q2 第 2 条：浮层触发是点按还是长按？

- **选项 A（推荐）**：**长按**（≥ 500 ms）。点按仍然输入字母。
  理由：点按是核心打字路径，全键盘连打时每键弹层会直接毁掉输入效率；长按机制已经在数字 / 标点键上跑了很久（`SoftKeyboardView.kt:590-596`），用户已有肌肉记忆。
- **选项 B**：点按弹层。
  若坚持，必须先回答：连打 `nihaoma` 时，8 次点按是否弹 8 次浮层？如果是，输入效率损失如何接受？如果不是（比如「第二次点按同一键才弹」），那实质上是长按的变体，不如直接用 A。

**推荐 A。**

**Q2-b（由 UX / 产品定，影响 AC-2.3）**：浮层里点选的角标字符，是否要经过「中文标点转换」？
- **选项 A（推荐）**：不转换，原样上屏（点 `~` 出 `~`，点 `,` 出 `,`）。角标字符是「精确取字符」，用户要中文标点会去逗号句号键的长按浮层或符号页。
- **选项 B**：按当前中文标点设置转换（点 `~` 出 `～`）。
  代价：同一按键的「主字符」和「角标字符」走两套转换规则，用户难以预测；且角标里有 `~ @ # % * ?` 这类本就无中文等价的字符，转换表需要逐个人工指定。

**推荐 A。** 现有实现天然是 A（浮层回调发的是 `KeyAction.CHAR`，`SoftKeyboardView.kt:855`），选 B 反而要新增转换表。

**Q3-1 识别条件**：
- **选项 A（推荐）**：连续两次「单字候选」上屏，间隔 ≤ 5 s，中间无任何其他上屏（标点 / 空格 / 英文 / emoji）、无面板操作、无光标移动。
- **选项 B**：只认「同一编码下连续选两个字」（如输入 `wq` 选「你」再选「们」）。
  代价：现实里两个字几乎不会同码，B 能覆盖的场景极少。

**推荐 A。** 时间窗 5 s 是估计值（五笔打两个四码字约 2–3 s，慢用户更长），**取值请 UX 用真机节奏复核**；AC-3.1/3.2 的边界值随最终 W 调整。

**Q3-2 词组编码来源**：
- **选项 A（推荐）**：一期只做五笔，按词组规则从两字全码推导（§3.3 已验证 99.82% 一致）。
- **选项 B**：五笔 + 拼音都做。拼音需「字 → 读音」反查 + 多音字消歧（`猫` 有 `mao`/`miao`），方案与工期都要重新评估。

**推荐 A，拼音进二期。**

**Q3-3 排序口径**：「按选择频次合理排序」现有机制已经满足——`weight = min(400, 120 + 10×count)`，用户词统一 +10 万压过系统词（`UserDictStore.kt:150`、`UserDictEngine.kt:28`）。**无需新排序规则**，只需保证词组被正确记录。
- 待确认：同码下用户词组是否允许**永远**排第 1？现有机制是「是」。若担心挤掉系统首选，可加「用户词组最多占前 1 位、其余按原序」——**推荐维持现状（永远第 1）**，因为这是用户自己造的词，优先级理应最高。

**Q3-4 误触保护**：
- **选项 A（推荐）**：三个保护同时生效——(a) 两次上屏的字相同且该词不在系统词库 → 不学；(b) 该词已存在于系统词库 → 不学；(c) 任一中断 → 不学。
- **选项 B**：只做 (b)(c)，不做 (a)（允许学「你你」这类叠字）。

**推荐 A**（`嘿嘿`/`呵呵` 这类叠字词基本都在系统词库里，会被 (b) 挡住，(a) 只会拦掉误触）。

**Q3-5 治理入口**：复用「用户词频学习」开关 + 设置页用户词库的删除 / 清空。
- **选项 A（推荐）**：不加新开关。
- **选项 B**：加「词组自学习」独立开关。代价：多一个开关、多一组文案、多一条静态校验。

**推荐 A。**

### Q4 第 4 条：接受「VOCA-30/56 为视觉基线，本批只补热区 + 方块键尺寸」吗？

- **选项 A（推荐）**：接受。字号 / 字重 / 圆角 / 键间距 / 键高 / 换行键全部归 VOCA-30/56/46，本批只做热区对齐 + 方块比例 + 40 dp 兜底（§4.3 已列去重表）。
- **选项 B**：不接受，本批另行定义一套视觉参数。
  代价：与三个在审 issue 直接冲突，`SoftKeyboardView` 会被改两遍，必返工。

**推荐 A。**

**Q4-b 必答**：用户说的「**定位偏移**」（点 A 出 B）现有 margin 解释不了（margin 只造成无响应）。请补一段复现视频或说明机型 / 手势设置；否则 AC-4.2 只能验「不丢键」，验不了「不错位」。

**Q4-c（已定，v1.1）**：间隙点击命中规则由 VOCA-68 交互规格 §5.3 自决为「**点落在哪个键格就命中哪个键**」，水平中线归左、垂直中线归上、十字中心归左上。原两个候选（最近中心 / 偏向下一个键）均不采用：最近中心对空格这类宽键会把右缘点击判给邻键，直接破坏「键面内必中」。判定口径见 §4.5 AC-4.1（C6）。

### Q5 第 5 条：补齐需求后再评估

- **选项 A（推荐）**：先只做 5a（一步填入），5b 挂起。5a 不改权限、不改架构，一周内可交付。
