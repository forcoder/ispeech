## 1. 条目一：快捷短语搜索框中间编辑

### 1.1 用户场景与目标

用户在快捷短语面板里搜一个长词（原文举例「用的请自行清理干净，放回原位！蟑螂」），发现中间打错一个字，只能从末尾一路退格删到那个字再重打。

**一句话目标**：让用户在不重输的前提下改搜索词的任意位置。**不做会怎样**：长词搜索的编辑成本约等于重输，用户改回用主输入框打字，面板的搜索能力被浪费。

### 1.2 现状（代码证据，不重新论证）

| 事实 | 位置 |
|---|---|
| 搜索框右侧已有 ✕，点击清空全部并重新聚焦 | `QuickPhrasePanel.kt:701-714`、服务侧 `IspeechImeService.kt:333` |
| 搜索词是服务侧一个 `String panelKeyword`，**只有整体替换，没有光标位置** | `IspeechImeService.kt:195`、`1343-1348` |
| 所有输入都是「追加到末尾」：软键盘字母、候选上屏、直接上屏、硬件键盘字母 | `IspeechImeService.kt:553`、`926`、`951`、`1344` |
| 退格只删末尾一个字符 | `IspeechImeService.kt:1350-1353` |
| 光标是一个自绘 `View`，插在文本后面固定位置，不随内容移动 | `QuickPhrasePanel.kt:691-694`、`render()` 恒 `setSelection(length)` |

**结论**：用户说的「没有清空按钮」与代码不符（可能是旧版 APK，见 §9 假设 A1）；真正的缺口是**没有光标位置这个概念**，因此无法中间插入/中间删除。

### 1.3 范围

**做**：光标左移 / 右移；在光标处插入字符；在光标处删除字符（删除光标前一个）；保留 ✕ 一键清空。

**不做**：
- 「新输入自动清空原有内容」（方案 ②）——不在本批，见 §7 Q1。
- 文字选区 / 复制 / 粘贴（新的编辑能力，需单独 issue）。
- 让搜索框弹出系统键盘（现有设计明确「不抢焦点」，见 `QuickPhrasePanel.kt:678-689` 注释；本批不推翻）。

### 1.4 可测验收标准

判定方式：`JVM` = 纯函数单测（无 Android 依赖）；`adb` = 真机/模拟器操作后读输入框文本或 `dumpsys`。

### 1.6 下一步 owner 建议

## 2. 条目二：字母键浮层（大小写 + 右上角角标）

### 2.1 用户场景与目标

字母键右上角印着小字（q 上是 1、a 上是 ~、z 上是 ( ），但点按只出字母，想打那个角标字符只能翻符号页；想打大写要先按 Shift。

**一句话目标**：一次长按拿到「该字母大小写 + 该键角标字符」。**不做会怎样**：角标字符是纯装饰，用户为了打 `(`、`~`、`#` 要切两次页面。

### 2.2 现状（代码证据）

| 事实 | 位置 |
|---|---|
| 字母键由 `letterKeys()` 生成：`output` 小写、`label` 大写、`hint` 取字符串对应位 | `KeyboardLayouts.kt:27-38` |
| 26 键的 hint 表：`qwertyuiop→1234567890`、`asdfghjkl→~!@#%""*?`、`zxcvbnm→()-—:;` | `KeyboardLayouts.kt:125-128` |
| 字母键的 `alt` 为空列表 → 没有长按浮层 | `KeyDef.char()` 默认 `alt = emptyList()`（`KeyDef.kt:160`） |
| 长按浮层只对 `alt` 非空的键生效（数字 / 标点 / 逗号句号） | `SoftKeyboardView.kt:590-596` |
| 浮层实现：`PopupWindow` + 横向条，每项 40×40 dp，点击后 `onKey(KeyDef.char(alt))` | `SoftKeyboardView.kt:832-877` |

**两个必须一起解决的现状缺陷**（否则浮层做出来也是错的）：

1. **`zxcvbnm` 只有 6 个 hint**（7 个字母）：`m` 的角标为空。浮层对 m 只能给 `m/M`。
2. **浮层选中的字符若走 `KeyAction.CHAR`，在中文态会进编码缓冲**：`handleChar()` 里 `mode != ENGLISH && !upper` 时一律 `buffer += lower`（`IspeechImeService.kt:655-675`）。也就是说，选「A」会变成往输入缓冲塞一个 `a`，而不是上屏 `A`。验收标准必须把这条钉死。

### 2.3 范围

**做**：长按字母键 → 浮层展示 `[小写, 大写, 角标字符]`（角标为空则只有前两项）；点选后**原样上屏**。

**不做**：
- 不改点按行为（点按仍是输入字母）。
- 不发明角标表以外的新字符（不自行扩展字符集）。
- 不做滑动选字（搜狗式 finger-slide 选择），本批只做点选。

### 2.4 可测验收标准

| ID | Given | When | Then | 判定 |
|---|---|---|---|---|
| AC-2.1 | 中文态字母页 | 长按 q 至系统长按阈值（`ViewConfiguration` 默认 500 ms）后再抬起 | 浮层出现，含 3 项 `q` `Q` `1` | adb |
| AC-2.2 | 同上 | 点 `1` | 宿主输入框出现「1」；输入法窗口不关闭、不跳页 | adb |
| AC-2.3 | 中文态字母页，「全角输出」关闭 | 长按 a → 点 `~` | 上屏「~」，**不被中文标点转换成「～」**（现状：浮层走 `KeyAction.CHAR` → `commitDirect`，不经 `PunctuationConverter`，天然满足） | adb |
| AC-2.4 | 中文态字母页 | 长按 a → 点 `A` | 上屏「A」，**编码缓冲为空**（随即输入 `wqiy` 应查「你」而不是把 A 混进码） | adb |
| AC-2.5 | 英文态字母页 | 长按 q → 点 `Q` | 上屏「Q」，且 Shift 状态不被改变 | adb |
| AC-2.6 | 浮层已弹出 | 点击浮层外空白 / 按返回 | 浮层消失，**不上屏任何字符** | adb |
| AC-2.7 | 任一字母键 | 生成浮层条目 | 顺序为 `[小写, 大写, hint]`，重复项去重（hint 与小写相同时只 2 项），条目数 ∈ {2,3} | JVM |
| AC-2.8 | 26 个字母键 | 生成本页浮层数据 | 每个键的 hint 为空或**恰好 1 个字符**；`m` 键要么补角标、要么明确为空（**现状 7 字母 6 角标，需修正**） | JVM |
| AC-2.9 | 中文态字母页 | 连按 q 三次，每击按压时长 ≤ 100 ms、间隔 ≤ 100 ms | 上屏「qqq」，全程不弹浮层（三次都是短按） | adb |
| AC-2.10 | 浮层已弹出 | 切面板 / 收起键盘 / 旋转 | 浮层随窗口消失，无残留 `PopupWindow`（`dumpsys window` 无游离窗口） | adb |

**异常态覆盖**：快速连按（AC-2.9）、中断（AC-2.10）、无角标键（AC-2.7/2.8）、空缓冲（AC-2.4）。

### 2.5 成功度量

「角标字符上屏次数 / 26 键字母上屏次数」——无埋点，**基线待补测**。本项不作验收门禁。

### 2.6 下一步 owner 建议

**UX**（必选）：触发方式与浮层层级（是否遮挡候选条）。**UI**：浮层外观需沿用键面设计令牌，不得新造魔法值。
输入：§7 Q2、Q2-b 的结论 + AC-2.1~2.10。

## 3. 条目三：词组自学习（手动拼接）

### 3.1 用户场景与目标

用户要打一个词库里没有的词（如「喂猫」），只能先打 `klge` 选「喂」、再打 `qtal` 选「猫」；下次打同一个词，还得重复一遍。

**一句话目标**：把「用户连续拼出来的两个字」记成词组，下次打对应的码就能直接选。**不做会怎样**：长尾新词（网络用语、昵称、方言词）永远靠逐字拼，这正是五笔用户最费力的场景。这是本批**用户价值最高**的一条。

### 3.2 现状（代码证据）

| 事实 | 位置 |
|---|---|
| 学习只发生在「选中候选」时，键 = 候选来源 + 当前编码 | `IspeechImeService.kt:1016-1030`、`1164-1174`、`909-918` |
| 用户词库按 `mode + code + text` 存，权重 `min(400, 120 + 10×次数)` | `UserDictStore.kt:150-153`、`171-180` |
| 用户词引擎统一 +100000 权重，保证压过系统词（系统词最大 65535） | `UserDictEngine.kt:24-30` |
| 手动连选两个单字 = 两次独立 `commit()`，每次清空 buffer，**不产生任何词组记录** | `IspeechImeService.kt:921-946` |
| 拼音态与五笔态分库（`cn` / `wb`），编码空间不互相污染 | `UserDictStore.kt` 的 `UserDictMode`、`AppContainer.kt:177` |

### 3.3 我在基线上做的数据核对（本轮新增证据）

词组编码不能靠猜。我把内置 `wubi86.dict`（165,599 行）按五笔词组规则全量回算了一遍：

| 词长 | 条数 | 按规则回算一致 | 不一致 | 一致率 |
|---|---:|---:|---:|---:|
| 2 字（首2+首2） | 66,534 | 66,413 | 119 | **99.82%** |
| 3 字（首1+首1+末2） | 11,295 | 11,287 | 6 | **99.93%** |
| 4 字（首1×4） | 11,618 | 11,616 | 1 | 99.99% |
| 5 字（首1×3+末1） | 706 | 706 | 0 | 100% |

- 不一致的 119 条集中在同部首字（`蹒跚` 实际码 `kakm`，按规则算 `khkh`），属词库自身的简码约定，不是规则错。
- 结论：**五笔 2 字词组的编码可由两个字的全码确定性推导**，可靠到可以直接写进验收标准。
- 复现方式：解析 `app/src/main/assets/wubi86.dict` 前 3 列，单字取「4 码且权重最高」那条全码，按上表规则拼接后与行内 code 比对。

**拼音没有这个性质**：拼音词组码要反查两个字各自的读音，多音字有歧义（`猫` 在 `pinyin86.dict` 里同时有 `mao` / `miao`），且用户词库会把音节间空格过滤掉（`UserDictStore.kt:95-98`），推导链更长、更脆。这是 §7 Q3-3 建议「一期只做五笔」的直接依据。

### 3.4 范围

**做**（一期）：
- 连续一次「单字候选上屏」+ 又一次「单字候选上屏」，间隔在时间窗内、中间无其他上屏 → 记为一个 2 字词组。
- 编码按五笔词组规则推导，写入 `wb` 用户词库。
- 复用现有「用户词频学习」开关（不新增开关）。
- 同码下该词组排在候选首位（复用现有 +10 万权重机制）。
- 治理沿用现状：设置页可见、可单条删除、可清空。

**不做**：
- 拼音态词组学习（二期，见 Q3-3）。
- 3 字及以上词组（二期）。
- 云端同步（另属 Roadmap `docs/sogou-feature-matrix.md` 第 58 行）。
- 词组「撤销上一次学习」的独立入口（设置页删除已覆盖，见 Q3-5）。

## 4. 条目四：按键触控热区与方块键尺寸

### 4.1 用户场景与目标

用户反馈「多次点击按键会出现点了没反应、定位偏移」，并希望按键接近搜狗白色方块键、触控范围与方框对齐。

**一句话目标**：手指落在键面方框内的任何位置都必须触发该键。**不做会怎样**：每次输入都随机丢键，这是**功能缺陷**级别的问题，不只是观感。

### 4.2 现状（代码证据 + 估算）

| 事实 | 位置 |
|---|---|
| 每个键四周各 4 dp `margin` → 相邻键之间有 8 dp 不可点区域 | `SoftKeyboardView.kt:119`、`485`、`521`、`539` |
| 键高默认 52 dp，字号 23 sp，圆角 10 dp | `SoftKeyboardView.kt:967`、`407-413`、`120` |
| 全仓**没有任何** `TouchDelegate` / `dispatchTouchEvent` 重写 → 死区里的触摸落到底层 `LinearLayout`，无人处理 | 全仓 0 命中 |
| 行首尾另有 3 dp padding | `SoftKeyboardView.kt:239` |
| 参照：搜狗同机实测字母键宽 120 px（36.9 dp）、键间距 6 px | `docs/keyboard-ui.md` §2 |

**死区面积估算**（按本机 1260 px / 3.25 = 387.7 dp 宽、10 列、行内 3 dp padding、键高 52 dp 计算）：

| keyMargin | 单键可点面积占键格比 | 死区占比 |
|---|---:|---:|
| 4 dp（现状） | 68.5% | **31.5%** |
| 3 dp（VOCA-30 目标态） | 75.6% | 24.4% |

> 这是**按布局参数算的模型值，不是真机实测**（本机无 `adb`，见 §9）。真机复测在 M3 做。

> **40 dp 触控规范对 26 键字母键不适用（本轮修正）**：387.7 dp 屏宽扣掉行内 3 dp 左右 padding 后
> 每格只有 **38.17 dp**（(387.69−6)/10），字母键**在物理上不可能达到 40 dp 宽**
> （搜狗同屏实测键宽 36.9 dp，同样不达标）。
> 因此 AC-4.6 对字母键只要求「填满自己的键格」（≥ 38 dp，即不留 margin 空隙），
> 40 dp 下限只对功能键 / 工具栏键 / 搜索框 ✕ 这类独立控件生效。若不这样拆，
> 验收时会用一个达不到的数字卡住实现。

**注意**：「定位偏移」（点 A 出 B）用 margin 解释不了——margin 只会造成「无响应」，不会造成「打到隔壁」。这条需要人类补复现视频才能定根因，见 §7 Q4-b。

### 4.3 与在审改动的去重结论（关键）

| 已在别处覆盖 | 出处 | 本批是否重复做 |
|---|---|---|
| 字母字号 23 → 18 sp、键间距 8 → 6 px、圆角 10 → 6 dp、换行键重设计、底行权重 | VOCA-30（`in_review`，`docs/keyboard-ui.md`） | **不做** |
| 候选词不加粗 | VOCA-56（`in_review`） | **不做** |
| 键高默认 52 → 46 dp、候选条改单行、双击空格、滑动翻页、按键音效 | VOCA-45 规格 → VOCA-46（`backlog`） | **不做**（含「整体缩小按键高度」这条，用户的诉求已被 VOCA-45/46 吸收） |

**本批真正剩下的只有三件**：① 可点区域与键面外框对齐（消死区）；② 方块键的宽高比例（在 46 dp 键高基准下仍是方块）；③ 独立控件（功能键 / 工具栏 / 面板按钮）的最小可点 ≥ 40 dp 兜底 —— 26 键字母键受屏宽限制只能到 38 dp，见 §4.2 注。

### 4.4 范围

**做**：键面外框 = 可点热区；方块键比例；字母键填满键格（≥ 38 dp 宽）、功能键与独立控件 ≥ 40×40 dp；改造后键盘总高相对合并后基线变化 ≤ 8 dp。

**不做**：任何字号 / 字重 / 配色 / 圆角 / 键高默认值 / 候选条结构 / 底行权重的改动（全部归上述三个 issue）。

### 4.5 可测验收标准

| ID | Given | When | Then | 判定 |
|---|---|---|---|---|
| AC-4.1 | 字母页 | 在相邻两键间隙中点按（margin 带中心） | 必须命中其中一键（**不得无响应**）；命中哪一键按 §7 Q4-c 的规则 | adb |

### 4.6 成功度量

「每次会话的丢键率」——**无法采集**（现无输入级埋点，`InputStats` 只记上屏次数，取不到「点了没出字」）。标注 **待补测**，采集方式：真机脚本按固定点位点击并比对输入框文本（AC-4.2 就是这个脚本的雏形）。本项不作验收门禁，AC-4.2 的 130/130 是门禁。

### 4.7 下一步 owner 建议

## 7. 待人类确认 / 待定（13 项，均给 2 个选项 + 推荐）

### Q1 第 1 条：清空方案选 ① 还是 ②？

- **选项 A（推荐）**：只做「光标定位 + 中间编辑」，保留现有 ✕。②「新输入自动清空」不做。
  理由：✕ 已提供一键清空（一次点击的成本已经很低）；② 会在用户想「在原词上接着打」时误删已有内容，且没有撤销。
- **选项 B**：A + 「新输入自动清空」做成设置项（默认关）。
  代价：多一个设置项 + 多一条状态：何时算「新输入」（打开面板后的第一个字符？还是光标在末尾的第一个字符？），歧义面大。

**推荐 A。** 若人类坚持 B，请一并回答：自动清空的触发点是什么。

### Q1-b 第 1 条：光标怎么移动？（UX 必答，影响 AC-1.3/1.4 的可操作性）

- **选项 A（推荐）**：面板内自带一对「◀ ▶」小键（放在搜索框右侧、✕ 左边）。
  理由：面板态下键盘已无方向键，硬件方向键被放行给宿主应用（`IspeechImeService.kt:561-566`），不加键就没有移动手段。
- **选项 B**：直接点搜索框文字位置定位光标。
  代价：搜索框刻意不持有 Android 焦点（`QuickPhrasePanel.kt:678-689` 明确写了抢焦点会导致跳页 / 按键被吞），点按定位要推翻这个设计，回归风险高。

**推荐 A。**

### Q2 第 2 条：浮层触发是点按还是长按？

- **选项 A（推荐）**：**长按**（≥ 500 ms）。点按仍然输入字母。
  理由：点按是核心打字路径，全键盘连打时每键弹层会直接毁掉输入效率；长按机制已经在数字 / 标点键上跑了很久（`SoftKeyboardView.kt:590-596`），用户已有肌肉记忆。
- **选项 B**：点按弹层。
  若坚持，必须先回答：连打 `nihaoma` 时，8 次点按是否弹 8 次浮层？如果是，输入效率损失如何接受？如果不是（比如「第二次点按同一键才弹」），那实质上是长按的变体，不如直接用 A。

**推荐 A。**

**Q2-b（由 UX / 产品定，影响 AC-2.3）**：浮层里点选的角标字符，是否要经过「中文标点转换」？
- **选项 A（推荐）**：不转换，原样上屏（点 `~` 出 `~`，点 `,` 出 `,`）。角标字符是「精确取字符」，用户要中文标点会去逗号句号键的长按浮层或符号页。
- **选项 B**：按当前中文标点设置转换（点 `~` 出 `～`）。
  代价：同一按键的「主字符」和「角标字符」走两套转换规则，用户难以预测；且角标里有 `~ @ # % * ?` 这类本就无中文等价的字符，转换表需要逐个人工指定。

**推荐 A。** 现有实现天然是 A（浮层回调发的是 `KeyAction.CHAR`，`SoftKeyboardView.kt:855`），选 B 反而要新增转换表。

**Q3-1 识别条件**：
- **选项 A（推荐）**：连续两次「单字候选」上屏，间隔 ≤ 5 s，中间无任何其他上屏（标点 / 空格 / 英文 / emoji）、无面板操作、无光标移动。
- **选项 B**：只认「同一编码下连续选两个字」（如输入 `wq` 选「你」再选「们」）。
  代价：现实里两个字几乎不会同码，B 能覆盖的场景极少。

**推荐 A。** 时间窗 5 s 是估计值（五笔打两个四码字约 2–3 s，慢用户更长），**取值请 UX 用真机节奏复核**；AC-3.1/3.2 的边界值随最终 W 调整。

**Q3-2 词组编码来源**：
- **选项 A（推荐）**：一期只做五笔，按词组规则从两字全码推导（§3.3 已验证 99.82% 一致）。
- **选项 B**：五笔 + 拼音都做。拼音需「字 → 读音」反查 + 多音字消歧（`猫` 有 `mao`/`miao`），方案与工期都要重新评估。

**推荐 A，拼音进二期。**

**Q3-3 排序口径**：「按选择频次合理排序」现有机制已经满足——`weight = min(400, 120 + 10×count)`，用户词统一 +10 万压过系统词（`UserDictStore.kt:150`、`UserDictEngine.kt:28`）。**无需新排序规则**，只需保证词组被正确记录。
- 待确认：同码下用户词组是否允许**永远**排第 1？现有机制是「是」。若担心挤掉系统首选，可加「用户词组最多占前 1 位、其余按原序」——**推荐维持现状（永远第 1）**，因为这是用户自己造的词，优先级理应最高。

**Q3-4 误触保护**：
- **选项 A（推荐）**：三个保护同时生效——(a) 两次上屏的字相同且该词不在系统词库 → 不学；(b) 该词已存在于系统词库 → 不学；(c) 任一中断 → 不学。
- **选项 B**：只做 (b)(c)，不做 (a)（允许学「你你」这类叠字）。

**推荐 A**（`嘿嘿`/`呵呵` 这类叠字词基本都在系统词库里，会被 (b) 挡住，(a) 只会拦掉误触）。

**Q3-5 治理入口**：复用「用户词频学习」开关 + 设置页用户词库的删除 / 清空。
- **选项 A（推荐）**：不加新开关。
- **选项 B**：加「词组自学习」独立开关。代价：多一个开关、多一组文案、多一条静态校验。

**推荐 A。**

### Q4 第 4 条：接受「VOCA-30/56 为视觉基线，本批只补热区 + 方块键尺寸」吗？

- **选项 A（推荐）**：接受。字号 / 字重 / 圆角 / 键间距 / 键高 / 换行键全部归 VOCA-30/56/46，本批只做热区对齐 + 方块比例 + 40 dp 兜底（§4.3 已列去重表）。
- **选项 B**：不接受，本批另行定义一套视觉参数。

## 10. 优先级建议（相对本批）

| 序 | 条目 | 优先级 | 理由 |
|---|---|---|---|
| 1 | 4 触控热区 | **P0** | 每一次输入都受影响；用户已明确反馈「点了没反应」。这本质是功能缺陷，不是样式优化。成本最低（改点在布局与命中判定），收益最直接 |
| 2 | 3 词组自学习 | **P0** | 用户价值最高（长尾词从「每次重拼」变成「一次记住」）。编码可确定性推导已验证，一期收窄到五笔 2 字后可做 |
| 3 | 1 搜索框中间编辑 | **P1** | 痛点真实但场景窄（长词搜索）；改动集中在面板状态机，风险可控。排在第 3 条之后，是因为它不改善核心输入路径 |
| 4 | 2 字母键浮层 | **P2** | 用户自己标「低」；且它是唯一会碰核心打字路径的改动，收益（少翻两页）与风险（连打被打断）不成比例 |
| 5 | 5a 一步填入 | **P2** | 小改动、无权限，可搭车做；但不解决任何输入效率问题 |
| — | 5b 通知触发的 AI 悬浮 | **不排期** | DoR 不满足（描述截断）+ 需通知读取权限 + 隐私合规未评估 |

> 与父 issue 用户自填优先级的差异：用户给第 3 条「中」、第 4 条「中」。我把第 4 条提到 P0，因为「点了没反应」是可用性缺陷而非优化项；把第 3 条提到 P0 并收窄范围，因为它覆盖的高频场景（新词）最广。若人类不同意这个排序，请直接改这张表，其余章节不受影响。
