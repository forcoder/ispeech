## 0. 结论速览

| # | 项 | 采纳 | 一句话规格 |
|---|---|---|---|
| 1 | 候选条空态 | **采纳（改语义）** | 空候选时候选条不消失，改为**恒定高度**：不随空态/组合态变化，消掉键盘跳动 |
| 2 | 双击空格出句号 | **采纳（默认关）** | 仅在「无组合、无联想、无面板、光标后是正文或行尾」时生效；时间窗 300 ms。搜狗 11.36 **出厂 `space_double_click_as_period = false` 已实测确认**（模拟器 `pm clear` 后直读 MMKV 字节 `01 00`） |
| 3 | 候选条横向浏览 | **采纳（模型已换）** | main `fa57a07` 起，候选条是**一条连续横排 + 连续横滚**，没有「页」。规格只钉 7 条可判约束（G1–G7），判据落在硬件键步长 **72 dp/次**、到界钳制、起手点归属、宿主文本不变上；旧版 40 dp 滑动阈值与「页」语义**作废**，见 §2.3 |
| 4 | 按键音效 | **不采纳（本期）** | 依赖新增音频资源与系统「触摸提示音」联动，收益低于成本；只补规格不做实现，理由见 §4 |
| 5 | 键盘手势删除（左滑退格） | **不采纳（本期）** | 与候选条水平滑动、以及输入法手势导航区的系统返回手势冲突面过大 |

占屏高（`fa57a07` 包、**模拟器口径 `emulator-5554` 440 dpi / font_scale 1.0，非目标设备结论**）：iSpeech 空态 **1050 px（44.87 %）**、组合中 **1056 px（45.13 %）**；搜狗 **978 px（41.79 %）**且组合中不变。
旧基线的 **+104 px 打字跳动已被 VOCA-185 收敛到 +6 px（2.2 dp）**，残余来源是「候选条高度仍由内容决定」，钉成恒高 46 dp 即归零。
收敛方案见 §6，推荐 **方案 B1** = 候选条恒高 46 dp + 键高 52→46 dp（现有 `KeyboardSize.COMPACT` 档）、`keyMargin` 保持 4，得 **989 px（42.25 %）**，相对搜狗 **+0.46 pp**，在「≤ +1 pp」门限内。
注意：**`keyMargin 3` 这个前提已失效** —— `07214d6` 把它连同 `keyRadius 6` 一起回退了，main 现状是 `keyMargin = 4`（§1.4）；再压到 3 会过冲成比搜狗矮 0.71 pp。

## 1. 实测证据（本轮新增，PM 交办的三件事）

### 1.1 双击空格：搜狗不输出句号

真机 `FMR0224913042917`，搜狗输入法，记事本 `notetext_textview`，用 `uiautomator dump` 读文本域真值：

| 输入法 | 前置状态 | 间隔 | 结果文本 | 判定 |
|---|---|---|---|---|
| 搜狗 | 空缓冲 | 150 ms | `'  '`（两个空格） | 无句号 |
| 搜狗 | 空缓冲 | 400 ms | `'  '` | 无句号 |

搜狗确实**有**这个功能，但**默认关闭**，且存在三个独立开关：

- 文案「双击空格添加句号」（`aapt2 dump strings` 命中 `string/b3k` 附近的「按键音效」同组资源）。
- 存储键：`space_double_click_as_period`、`space_double_click_as_period_en_nine`、`space_double_click_as_period_en_pro`。
- 真值存储位置：`/data/data/com.sohu.inputmethod.sogou/files/mmkv/com.sohu.inputmethod.sogou.foreign_settings`（MMKV，**不是** `shared_prefs`）。
  实测字节：键名后紧跟 `01 00`，即 bool=`false`（偏移 692）。`shared_prefs` 里根本没有这个键 —— 之前往 `shared_prefs` 注入无效，原因就在这里。

> **第二轮复核（2026-11-10，模拟器 `emulator-5554`，root）**，把开关与效果彻底分开，修正上一轮的测量瑕疵：
>
> 1. **出厂值 = 关（硬证据）**：`pm clear com.sohu.inputmethod.sogou` 后直读 `foreign_settings`，键名后字节为 `01 00`，即 `bool=false`；`shared_prefs` 里没有该键。上一轮读到的 `01 01` 是被人为改过之后的状态，不是出厂态。
> 2. **写入 true 后仍不出句号**：先 `am force-stop` 再 `dd` 写盘（避免 MMKV 内存副本回写覆盖），复查字节确为 `01 01`，重启搜狗后重测：间隔 100/200/300/450/700 ms × 「空缓冲直出」与「拼音组合中」两态，**全部只得到两个半角空格，无 `。` 也无 `.`**；三连击得到三个空格。
> 3. **测试通道限制（必须标注）**：本轮用 `input keyevent 62` 而非触摸点击 —— 搜狗键盘是自绘 View（窗口 `fillxfill`、无 uiautomator 节点），坐标法在该模拟器上反复漂移，落键自证不通过。`keyevent` 与真实触摸在 `handleSpace()` 侧是否等价**未验证**。因此「开启后不出句号」这条的强度低于「出厂默认关」那条。
>
> **净结论（不变）**：搜狗 11.36 开箱不给句号。规格里的 300 ms 仍是自定值。

### 1.2 搜狗候选条横滑翻页：结论不确定，按「不依赖它」处理（历史证据，作用对象已被 §2.3 替换）

这一条我**没能拿到干净证据**，如实写清楚，不编结论。

真机（`FMR0224913042917`）单次观察：

- 在候选条内水平滑动 `1000→600`（400 px / 123 dp）后，候选列表签名改变、组合码不变、文本域不变 → 当时判为「翻页成立」。

但在受控复测中这个结论**不成立**：

| 环境 | 用例 | 结果 |
|---|---|---|
| 真机 | 多次受控扫描（不同距离、加 0px 点击对照） | 每个手势（含纯点击）都会改变候选区签名 → 度量本身无效 |
| 模拟器 `emulator-5554` | 条内左滑 400 px | 候选变、组合码变、**文本变** → 是**上屏候选**，不是翻页 |
| 模拟器 | 条内右滑 400 px / 0px 点击 / 条外滑动 / 键区滑动 / 条内左滑 150 px | 全部无变化 |

结论：**搜狗 11.36 在实测环境里没有表现出可靠的「候选条横滑翻页」行为**；唯一能复现的效果是「滑动被当成点击上屏了候选」。

**第二轮复核（2026-11-10，模拟器，冷启动 + 出厂态）** 补了两条量化数据：

| 用例 | 结果 |
|---|---|
| 候选带内 `y=1500` 左滑 800 px（300 ms）| 候选区像素哈希 `7b9ab345e953` → `7b9ab345e953`，**未变** |
| 硬件翻页键 `KEYCODE_EQUALS`（搜狗「减号等号」翻页方案）| 同一哈希，**未变** |

第二条尤其关键：连**专用翻页键**都不改变候选区，说明当时并不存在「可翻的候选页」（候选条为空或只有一页），而不是「滑动没被识别」。这也解释了第一轮「有时变、有时不变」的抖动 —— 变化来自候选条自身的动画/时钟，不是翻页。

因此本规格**不把「对齐搜狗」当作横滚的依据**，改为按我们自己的可用性需求定义（§2.3），并在 §9 明确标注搜狗侧未证实。

> **2026-11-16 更新**：本条结论的作用对象变了。main 已把候选条改成**连续横滚**（`fa57a07` / VOCA-185），「翻页」这个单位不存在了，所以本节的「搜狗未证实」不再需要由我们自己补一个阈值 —— 旧版那个自定的 **40 dp 位移阈值已随 §2.3 一起作废**（实测触摸位移经 fling 叠加后根本不可复现，§2.3 F5）。本节证据本身不变。

### 1.3 按键音效：搜狗有开关，默认关

搜狗 11.36 的 `shared_prefs/com.sohu.inputmethod.sogou_preferences.xml`（模拟器 root 直读）：

```xml
<boolean name="keyboardfeedback_volume_switch" value="false" />
<boolean name="keyboardfeedback_vibration_switch" value="false" />
<boolean name="pref_keyboardfeedback_linear_motor_vibration_switch" value="false" />
<boolean name="pref_use_talkback_keyboard_specal_vibrate" value="true" />
<int     name="pref_vibrate_value_keyboard_feedback" value="5" />
```

- 按键音开关 **默认 false**；按键振动 **默认 false**；TalkBack 专用振动 **默认 true**。
- 文案里有「无障碍模式下，我们会为您自动开启按键音和按键振动」—— 即音效的启用条件是**无障碍模式**，不是普通模式。
- 真机侧 `settings get system sound_effects_enabled` = **0**（系统触摸提示音关闭）。
- 未测到：真机（无 root）上打开音效后的实际播放行为，因搜狗设置页在真机上无法稳定进入。**不推测波形/音量**。

**第二轮复核（2026-11-10，模拟器，root）** —— 把「测不出来」的原因查清了，不是方法问题：

| 检查 | 结果 | 含义 |
|---|---|---|
| 系统 UI 音效资源 | `/product/media/audio/ui/` 有 24 个文件，含 `KeypressSpacebar.ogg`、`KeypressStandard.ogg` | 系统侧资源**齐全**，排除「没资源可放」 |
| `settings system sound_effects_enabled` | 改 `1` 后复读仍为 `1`，但按键**仍无任何音频事件** | 开关不是唯一前置条件 |
| `dumpsys media.audio_flinger` track 计数 | 按键 6 次：`28463 → 28461`（-2，噪声级） | **无新建 track** |
| 阳性对照：`input keyevent 24`（音量键，系统必响） | `af_len` 仅 +157 字节（dumpsys 文本抖动），track 数 `0 → 0` | **阳性对照失败** |

阳性对照失败是关键：连系统保证会发声的音量键都测不到 track，说明这台 headless 模拟器**没有可用的音频输出后端**，任何「有声/无声」的判断都不成立。

> 所以音效这一项的性质是：**本环境物理上无法测量**，不是「测了没声」。结论只能是「未测到」，且**不得**据此写「搜狗按键无声」。

`product` 分区而非 `system` 分区也解释了一个容易踩的坑：在旧版 AOSP 镜像上 `/system/media/audio/ui` 不存在，按老路径检查会误判成「没有音效资源」。

### 1.4 键盘占屏：组件级拆解（2026-11-16 在 `fa57a07` 包上重测，**模拟器口径**）

> **口径（必读）**：本节全部数字来自 `emulator-5554`（Android 14 / API 34，1080×2340，density 440，`font_scale` 1.0）+ `fa57a07` 构建的包。**不是目标设备结论** —— 真机 `FMR0224913042917`（520 dpi / `font_scale` 1.15）上从未装过 `fa57a07` 口径的包。质检在 2026-11-16 于真机测得「空 1052 → 组合 1180（Δ +128 px）」，但那台机上装的是**翻页版旧包**（`versionName 1.6`、资源含 `candidate_page_*`），**不能**用来否定也不能用来确认本节的 +6 px；它唯一证明的是 **Δ 不是设备无关量**（随 build 与 `font_scale` 变化），所以 §9.1 的「真机复跑」是硬前提（该数据点原文见 §9 表头与 §9.1）。

**为什么必须重测**：本节原数据来自 2026-11-09 真机 + `f3df320` 包。此后 main 上落了 VOCA-29（工具栏）、VOCA-185（候选条改单行连续横滚，删掉页码器/翻页箭头/齿轮）、`f728231`（UI 恢复）、`07214d6`（**把 VOCA-30 的 `keyMargin 3→4`、`keyRadius 6→10` 回退**）。旧的 1092 / 1196 px 与「+104 px 跳动」都不再是现状。

**取数口径（两个坑，必须写清）**

1. **API 34 上 `mImeHeight` ≠ 真实占屏**：`dumpsys window displays` 的 `InsetsSource id=N type=ime frame=[0,1290][1080,2340]` 才是 IME 实际占据的像素区，`mImeHeight` 比它少 **66 px**（导航条）。本文一律以 **frame 高度**为占屏口径，`mImeHeight` 只用于和旧数据对账。
2. **PM 指定的 `tools/verify/measure_ime_inset.py --compare` 本轮跑不出可比结果**，两条都是事实而非选择：
   - 该脚本**不在本分支、也不在 main**，只在 `origin/agent/agent/voca-37`（commit `8b8a7eb`），需 `git show` 取出。
   - 它的正则写死 `InsetsSource type=ITYPE_IME frame=`（旧 dumpsys 格式），Android 14 已改为 `InsetsSource id=N type=ime frame=` → API 34 上匹配不到，直接报「键盘没弹出」。
   我用它的**同一口径与换算**在本地跑通并交叉验证了上面的数字（只放宽正则，改动未提交 —— 属工具侧缺陷，建议新开 issue 交测试/工具维护者修）。它 `--compare` 打出的「搜狗 0 px」是**假值**：脚本 `ime set` 之后没有重新点输入框，键盘根本没弹。

**旧数据保留备查（2026-11-09 真机 / `f3df320`，已过期）**：iSpeech 1092 → 1196 px（+104）、搜狗 985 px、chrome 96 vs 68.3 dp、键区 4 行 780 px。这些数字对应的两行候选条与 `keyMargin 3` 都已不在 main 上，**不得再用于判定 AC-1 或 §6.2**，只作为「跳动已被收敛 94 px」的趋势对照。

**残余 6 px 的机制（代码可解释，与旧结论同一类问题）**：`candidate_view.xml` 现在是**横向单行**结构 —— 组合码 chip `candidate_code`（`candidate_view.xml:19-30`）与 `candidate_scroll`（`:33-40`）同一行，空态两者一起 `GONE`（`CandidateView.kt:69` `codeLabel.visibility`、`:77` `scrollView.visibility`），组合态两者都 `VISIBLE`（`:79`）。根布局用 `minHeight`（`candidate_view.xml:11` `android:minHeight="44dp"`）而不是固定 `height`（`:8` `layout_height="wrap_content"`），所以：

| 状态 | 内容高度 | 根布局取值 | 实测 |
|---|---|---|---|
| 空候选 | 0 | `max(44dp, padding 8dp)` = 44 dp | 122 px = 44.4 dp |
| 组合中 | 候选行 `minHeight 38dp` + padding 8dp = 46 dp | `max(44dp, 46dp)` = **46 dp** | 128 px = 46.5 dp |

**仍然有一个 `sp` 风险没消掉**：候选项字号是 `textSize = 18f`（sp 单位）+ 上下 `dp(6)` padding。本轮模拟器 `font_scale = 1.0`，内容刚好被 `minHeight 38dp` 兜住；真机 `font_scale = 1.15` 下文字行高会顶过 38 dp，**候选条就会再往上长**。旧基线那 +104 px 就是这么来的（真机 1092→1196 vs 模拟器 990→1084，像素与 dp 增量都不一致，证明它不是常量）。

> 规格要求因此必须是「**固定高度**」而不是「`minHeight` + 内容」：见 §2.1 实现约束 2 —— 恒高 46 dp 只有在真机 `font_scale=1.15` 下也测得 Δ=0 才算成立，AC-1 必须回真机复跑（§9.1）。

## 2. 五项交互规格

### 2.1 候选条空态

**触发**：`CandidateView.update()`（`CandidateView.kt:67`）被调用且 `list.isEmpty()`（`:76`），当前在 `:69` / `:77` 把组合码 chip 与候选行一起 `GONE`，**条自身常驻不收起** —— 这个结论保持。

**规格**：候选条「**单行 + 固定高度**」。单行这半已经由 `fa57a07`（VOCA-185）落地，本规格现在只剩**恒高**这一条没做：高度钉死 **46 dp**，不随空态/组合态变化。

| 状态 | 内容（同一行，从左到右） | 规格高度 | **fa57a07 实测** |
|---|---|---|---|
| 空候选 | 组合码区留白 + 候选区留白（无齿轮、无翻页器） | **46 dp，固定** | 44.4 dp（122 px）❌ |
| 有候选 | 组合码 chip + 连续候选词 | **46 dp，固定** | 46.5 dp（128 px）✅ |

**为什么这条只剩「恒高」**（2026-11-16 现状核对，旧推演的落点）：

- 旧版这里论证的是「单行 vs 两行钉高」，因为当时 `candidate_view.xml` 是竖向两行、组合态多撑 104 px。VOCA-185 已经把它改成横向单行，**跳动从 +104 px 收敛到 +6 px**（§1.4），旧推演的两个前提（两行结构、chrome 96 dp）都不成立了，故删除。
- 残余 6 px 完全由「根布局用 `minHeight` 而非固定 `height`」造成：空态塌到 44 dp、组合态被内容撑到 46 dp。**改法是一行 XML**，不是结构改造。
- 「恒高」仍然必须是**固定高度**而不是 `minHeight`：候选字号是 sp，真机 `font_scale=1.15` 下内容会顶过 38 dp 的行高，`minHeight` 兜不住（§1.4 的 sp 风险）。

**实现约束**：

1. 候选条根布局 `layout_height` / `height` 钉成 **46 dp**，去掉「内容决定高度」的路径；`minHeight` 可保留但不作为唯一手段。
2. 空态只把 `codeLabel`、`scrollView` 置 `GONE` 或清空 `itemContainer`，**不得改变容器高度**（现状已满足）。
3. 组合码 chip 保持行内最左、**不随横滚移动**（实测滚到最右 chip 仍在 x≈0，符合预期）。
4. 高度 46 dp 下必须仍能完整显示候选文字：`textSize 18sp` + 上下 `dp(6)` padding 在 `font_scale 1.15` 下约 33 dp，加 chip 与行 padding 仍在 46 dp 内 —— 真机复跑 AC-1 时一并验证（§9.1）。

**理由**：候选条高度变化会把整个键盘往上顶（键区像素位置不动，只有顶边上移），用户每次开始打字都会看到一次跳动。搜狗同为单条结构且组合态 Δ=0（§1.4）。

**副作用（必须接受）**：单行后**横向空间变紧** —— 组合码 chip 约占 110 px（模拟器实测），剩余给候选词。规格要求：候选区保持 `HorizontalScrollView` 连续横滚（已实现），并保证**至少完整显示 4 个候选**；不足时优先牺牲 chip 的显示宽度（`ellipsize=END`）而不是候选数。

> 这句「≥4 个完整候选」2026-11-17 起**有对应验收项了：AC-10**（在此之前它是散文，四轮取证都没落到它头上）。判据、两档口径、长词冲突的归属见 §4 AC-10。

**冲突与优先级**：
- 与「候选条空态收起」相反 —— 本规格明确选择常驻 + 恒高。
- 「候选条改成单行」的产品取舍（§7 #1）**已由 VOCA-185 落地**，且比我们规格更彻底（连翻页器、页码、齿轮一起删）；剩下的恒高改动不再需要新的确认。

**状态覆盖**（输入态 × 候选态 × 面板态）：见 §3 矩阵。

### 2.2 双击空格出句号

**触发**：`handleSpace()`（`IspeechImeService.kt:707-729`）—— 由软键盘 `:447`（`KeyAction.SPACE -> handleSpace()`）与物理键 `onKeyDown`（`:525` 起）里的 `:585` 共用。

现有 `handleSpace()` 的优先级链条是：
`t9Digits` → `buffer` → `aiReplyActive` → `voiceActive` → `associationActive` → 直接输出空格。

**规格 —— 双击只在「链条走到底、且上一次上屏也是空格」时生效**：

```
space 按下:
  1. t9Digits 非空              → commitT9()            （不变）
  2. buffer 非空                → commitTop()           （不变）
  3. aiReplyActive              → commitAiReply()       （不变）
  4. voiceActive                → commitVoice()         （不变）
  5. associationActive          → pickCandidate(0)      （不变）
  6. 以上都不成立:
       if 距上次「空格上屏」≤ 300ms 且 中间无其他上屏/删除/移动光标:
           deleteSurroundingText(1,0)   # 删掉第一个空格
           commitText("。")              # 中文标点开启、非英文态
       else:
           commitDirect(" ") 并记录 lastSpaceCommitAt
```

**关键规则（必须有，否则会打架）**：

| 规则 | 内容 |
|---|---|
| R1 | 第二次按键的净效果是**「两个空格变成一个句号」**：先删掉已上屏的那一个空格，再上屏「。」。**不是**「两个空格后再补一个句号」。实现上对应 `deleteSurroundingText(1,0)` + `commitText("。")`，两步要放在同一次 `InputConnection` 编辑批次里，避免中间态被输入法/宿主看见。 |
| R2 | 判定窗口 **300 ms**（`DOUBLE_TAP_MS = 320L` 已存在于 `SoftKeyboardView.kt:988`，规格取 300 ms 与之同量级；实现可复用该常量）。 |
| R3 | 任何**非空格**上屏（候选、标点、字母、语音、AI）都清零 `lastSpaceCommitAt`。 |
| R4 | 退格、移动光标、切换面板、切换输入法、切换中英，同样清零。 |
| R5 | 有候选时**永远先上屏首选**，双击逻辑不参与 —— 这是本条最重要的冲突点。用户连按两次空格想打句号，第一次就会把首选词上屏，第二次变成普通空格。 |
| R6 | `chinesePunctuation = false`（`app/src/main/java/com/ispeech/settings/store/KeyboardSettings.kt:21`，默认 `true`）或英文态（`mode == InputMode.ENGLISH`，见 `IspeechImeService.kt:286`）→ **不转换**，输出两个空格（对齐搜狗：搜狗英文态也不加句号）。 |
| R7 | 光标前一个字符已经是「。！？；」等句末标点时仍生效（不做智能判断），避免「有时灵有时不灵」。 |
| R8 | **不与空格长按语音冲突**：空格已绑 `installSpaceGesture`（`SoftKeyboardView.kt:684`，按住 500 ms 进语音，阈值来自设置 `voice_space_long_press_ms`）。双击是**两次独立点击**，每次点击的按住时长都远小于 500 ms，因此不会误触语音。规格要求：双击判定必须在服务侧 `handleSpace()` 做（已经如此），**不得**改成 View 层的双击手势，否则会与长按 runnable 抢事件。 |

**默认值**：**关闭**（`KeyboardSettings` 新增 `doubleSpacePeriod: Boolean = false`），设置页给开关「双击空格添加句号」。
理由：这是我们自己的新行为，默认开启会改变既有用户的手感；且搜狗自身也默认关闭。

| **G6** | 触摸位移**不设自定义阈值**（横滚是连续量，没有「一步」）。点选的成立条件是 **UP 相对 DOWN 的合位移 < `scaledTouchSlop`（8 dp，两轴都算）** —— 不是只看横向分量。<br>⚠️ **2026-11-17 修正**：旧版这里写的「位移 < slop 视为点选，沿用平台判定」不准确。平台只在**外层可滚动容器**要不要抢占时用 slop，`HorizontalScrollView` 抢占只看横向分量；候选项自己是裸 `View` 点击语义，判定只看「UP 落点是否还在自身边界（外扩一个 slop）内」，**中途竖向位移多大都不取消点击**。结果就是 F12：dx 绝对值 < slop 且 dy ≤ 项高 → 横滚不抢占、点选也不撤销 = 上屏。要拿到本条写的语义，实现侧必须自己加竖向 slop 判定（AC-11 的修复口径） | 点选用例 F10；误上屏用例 AC-11；禁用 F5 类判据 |
| **G7** | 角标与选择入口一致：只有 1–9 有数字键入口，**第 10 项起不显示数字角标**（或换成不承诺具体按键的样式） | 滚到后段截图：出现的角标数字 ≤ 9 |

**为什么判据不能写成「滑多少算一步」**：F5 —— 触摸位移经 fling 叠加后与手指位移不成比例（手指 600 px 只滚 330 px，400 px 反而滚 380 px）。任何写死 dp 的触摸阈值在这台机器上连跑两遍都过不了。可量化的只有 G5 的硬件键步长，这也是 AC-4 用它做主证的原因。

**已知缺陷（本轮实测发现，规格只记录、不在本 issue 修）**：

1. **G7**：第 10–27 项显示数字角标但无按键入口 —— 用户按角标找键会找不到。
2. **G2**：`update()` 的非空分支无条件 `scrollTo(0,0)`，所以「候选集没变但被重新刷新」的动作（面板开关、联想回填等）会把用户已经滚出来的位置甩回最左。要构造稳定用例得先有一个「不改候选内容的 update」触发点，本轮**未测到**（§9.4）。

**与旧规格的差异**

| 旧条款（2026-11-09） | 处置 | 原因 |
|---|---|---|
| 水平位移 ≥ 40 dp 翻一页 | **删除** | 无「页」；且触摸位移不可复现（F5） |
| `abs(dx) > abs(dy) × 1.5` 才算水平手势 | **删除**，改为 G4「起手点优先」 | 实测斜滑由 `HorizontalScrollView` 直接抢占，不需要自判方向（F7） |
| 翻页成功时 `performHapticFeedback(VIRTUAL_KEY)` | **移出规格** | 横滚是连续动作，没有「翻页成功」这个离散事件可挂反馈；振动仍由按键反馈覆盖 |
| 首页右滑 / 末页左滑 no-op、不循环 | **保留**，语义换成左右边界（G3） | 结论与平台行为一致 |
| 与候选点击 / 长按的冲突处理 | **保留结论**，实现方式改为「点选 = UP 相对 DOWN 合位移 < 8 dp + 长按优先」（G6）｜⚠️ 2026-11-17：原写的「沿用平台 touch slop」在竖向不成立，见 F12 / AC-11 | 旧 8 个手势用例 0 次误上屏只覆盖**横向**与点/长按（F9/F10）；带内近垂直短拖（F12）当时没测，实测会上屏 |
| 与翻页器 `DISABLED_ALPHA` 置灰表现一致 | **删除** | `fa57a07` 无翻页器 |
| 响应区域仅 `candidate_scroll` bounds 内 | **保留**（G4） | 与实测一致 |

**不做**：竖向滑动浏览候选、上下滑翻页（搜狗侧未证实，§1.2；平台也无对应行为）。

> **「不做」= 这个手势没有功能，不等于它可以有副作用**（2026-11-17，AC-11 的裁决依据）：带内近垂直拖动既不是横滚也不是点选，功能面为空，所以它必须**什么都不做**；现在它上屏了一条候选，就是缺陷，而不是「未定义行为可以随便」。

### 2.4 按键音效 —— 不采纳（本期）

**理由（按门禁要求写明，不静默丢项）**：

1. 搜狗自身的按键音**默认关闭**，且只在无障碍模式下自动开启（§1.3）。也就是说「对齐搜狗」的正确结论是**保持关闭**，而不是加音效。
2. 实现需要引入音频资源（`res/raw/*.ogg`），会增大 APK；且必须正确处理 `Settings.System.SOUND_EFFECTS_ENABLED` 与静音/勿扰模式，否则会出现「静音了还响」的严重缺陷。
3. 真机上无法验证播放效果（无 root、搜狗设置页进不去），按门禁「无实测证据不写规格」的原则，只能标未测到。

**本期替代**：维持现有 `performHapticFeedback(VIRTUAL_KEY)`（`SoftKeyboardView.kt:759`），并在设置页把「按键震动」开关的默认值与说明文案补齐。
若后续人类明确要求音效，建议新开 issue，规格要点：默认关、跟随系统 `sound_effects_enabled`、勿扰模式静音、音量取 `AudioManager.FX_KEY_CLICK`。

### 2.5 键盘手势删除（左滑退格）—— 不采纳（本期）

**理由**：

1. 与 §2.3 的候选条水平滑动**在同一方向上抢手势**，两个都做会让用户无法预测结果。
2. 键盘区域紧贴屏幕底部，正是 Android 手势导航的「返回」热区；在键面上做左滑会与系统返回手势冲突，且我们无法可靠区分（`View` 层拿不到系统手势的拦截结果）。
3. 搜狗的实现落在**删除键自身**（长按连删 + 滑动），而不是「键盘任意位置左滑」。这个我们**已经实现**（`startRepeatDelete()`，`SoftKeyboardView.kt:765`），所以「手势删除」的真实缺口并不存在。

**保留项**：长按删除键连续退格（现状已实现，规格要求保留 `REPEAT_START_DELAY_MS=380 / SLOW=90 / FAST=45`）。

### AC-1 候选条空态高度不变

```
Given  设备已设 iSpeech 为默认输入法，任一文本编辑器获得焦点，键盘已弹出（空候选）
When   记录 `InsetsSource type=ime` 的 frame 高度 H0，然后输入 4 个字母形成组合（有候选），再记录 H1
Then   H1 − H0 = 0
```

**`fa57a07` 实测（`emulator-5554`，2026-11-16）**：`1050 → 1056`，**差 +6 px = +2.2 dp，本项仍不通过**（5/5 次复现；`mImeHeight` 口径同向 984 → 990）。
旧基线的 +104 px 跳动已被 VOCA-185 的单行改造收敛掉 94 px，**剩下的 6 px 就是「候选条高度仍由 `minHeight` + 内容决定」**—— 按 §2.1 钉成恒高 46 dp 即归零，改动量是一行 XML。

> 判定只看**差值**，不看绝对值 —— 不同设备/密度/导航条下绝对值本来就不同。
> **取证状态（2026-11-16 整改轮明确）：本条未在目标设备取证，只有模拟器口径（`emulator-5554`，`font_scale=1.0`）。**真机 `font_scale=1.15` 下 sp 字号可能把候选行顶过 38 dp，Δ 会重新变大（§1.4、§9.1）。要定稿需要：①人类确认把 `fa57a07` 口径的包装上真机 `FMR0224913042917`（项目规则五：装真机属生产操作，agent 不擅自执行），②按 §8.1 复跑并贴 `dumpsys window displays` 的 `type=ime frame`。**在此之前 AC-1 的「+6 px」只能作为模拟器结论引用。**

### AC-3 双击空格不与「上屏首选」打架

```
Given  中文输入态（拼音或五笔任一）、已输入组合码且有候选、双击空格开关开启
When   在 300ms 内连按两次空格
Then   第一次空格上屏首选词，第二次空格输出一个普通空格
And    文本域中不出现 "。"
```

> **Given 为什么写「拼音或五笔任一」**（2026-11-17 修订，VOCA-47 打回项 4，洞察BA 裁决 `docs/requirements/VOCA-47-acceptance-ruling.md` §4）：双击判定链**没有输入法方案分支** —— `SpaceKeyPolicy.decide()`（`SpaceKeyPolicy.kt:72-90`，行号锚 `c524351`）只看 `t9Pending / composing / aiReplyPending / voicePending / associationPending`（`:77-81`）与 `doubleSpacePeriod / chinesePunctuation / englishMode`（`:83`），英文态只判 `state.englishMode`（同一个短路里，不区分五笔 / 拼音）；句号是常量 `"。"`（`IspeechImeService.kt:108`），`convertHan()`（`:1394`）只做简→繁，不读方案；`InputMode.kt:5-6` 的注释本身就写明「五笔与拼音都是『中文态』」。→ AC-2 / AC-3 的 Then 在两态走同一条链、同一个输出，**拼音态取证即可判定，不需要补五笔复跑**。
> 两个短路开关的读数必须与判定同批给出，缺一项这条就退回「无法核实」：`doubleSpacePeriod`（开关态）、**`chinesePunctuation`**（排在双击判定之前，关了就直接出两个空格）。
> **失效条件**：`decide()` 的参数表一旦引入 `ChineseInputMethod` 分支（两态走不同判定），本段等价依据作废，必须补五笔复跑。

### AC-4 连续横滚生效（用硬件键步长定标，唯一可复现口径）

```
Given  iSpeech 为默认输入法，宿主输入框获得焦点，键盘已弹出，输入 `g` 使候选条出现远超一屏的候选
       （实测 27 条 / 可滚范围 ≈ 4024 px，一屏约 6 条）
When   截屏 S0；按一次 KEYCODE_EQUALS(70)；等 500 ms；截屏 S1
Then   S1 的候选带（y=1284–1411 全宽）列灰度剖面相对 S0 **左移 198 ± 6 px**（= 72.0 ± 2 dp），互相关残差 ≤ 5
And    连按 3 次（每次间隔 500 ms）的累计位移 = 单次位移 × 3，容差 ± 10 px —— 证明是定步长，不是随机 fling
And    宿主文本域内容仍是组合码 `g`（滚动不产生上屏）
```

取数：`adb shell input keyevent 70` + `adb exec-out screencap -p` + 列剖面互相关（§8.4）。
**禁止用触摸滑动做本条判据**：实测手指 100/200/400/600 px → 滚动 94/256/380/330 px，非单调、不可复现（§2.3 F5）。触摸路径的正确性由 AC-6/AC-7 的「不该动的没动」反向覆盖。

### AC-5 左右边界不循环

```
Given  同 AC-4
When   连按 KEYCODE_EQUALS(70)，每次间隔 450 ms，直到候选带与上一帧逐像素相同，记到界次数 K（实测 K = 21，到界前累计位移 4024 px）
Then   第 K+1、K+2、K+3 次的候选带与第 K 次**完全相同**（像素差 bbox = None；实测连续 9 对相邻帧全同）
And    改按 KEYCODE_MINUS(69) 一次后候选带位移 = −198 ± 6 px → 证明没有循环到最左
And    全程宿主文本域内容不变
镜像   在最左端连按 KEYCODE_MINUS 3 次 → 候选带完全相同；再按 `=` 恢复位移
```

> **实测已通过（现状即合规）**：本条测的是**平台 `HorizontalScrollView` 的钳制行为**，`fa57a07` 未覆写 `onOverScrolled`/`overScrollMode=never`，所以 Stage 2 只要不引入循环逻辑就保持通过。它是回归护栏，不是待修项。

### AC-6 起手区约束（带外手势不得驱动横滚）

```
Given  同 AC-4，候选带偏移为 0
When   在键区第 2 行水平滑动 600 px：`input swipe 300 1780 900 1780 250`
Then   候选带列剖面位移 = 0 px
```

### AC-11 候选带内近垂直短拖不得上屏（2026-11-17 新增，本轮不测）

**起因**：VOCA-47 返修轮的观察项（`tools/qa/voca-37/evidence/ev_vswipe_a.txt`，440 dpi，`band=[1353,1477]`，起手 y=1391）。带内纯竖向拖动，落点仍在带内时宿主文本从 `shi` 变成 `是` —— 上屏了一次：

| dy | 落点 y | 相对候选带 | committed |
|---|---|---|---|
| 40 / 60 / 80 | 1431 / 1451 / 1471 | 仍在带内 | **True** |
| 110 / 150 / 200 | 1501 / 1541 / 1591 | 出带 | False |
| 对照：纯 tap（dy=0） | 1412 | 带内 | True（预期行为） |

**UX 裁决：算误上屏（缺陷）。** 判据不是「划动的幅度多大」，而是**这个手势有没有被定义**：§2.3 给候选带只定义了两件事 —— 横向拖动 = 横滚、点击 = 上屏该项。纯竖向移动**没有任何被分配的功能**，一个未定义手势不该产生有害副作用。危害是实打实的：上屏的是落点所在那一条候选，组合码被吃掉，用户只能靠退格回滚，而这一下往往发生在「想划一下看看」的时候。

**根因（读码 + 几何对账）**：候选项是 `isClickable = true` + `setOnClickListener`（`fa57a07` 与 `c524351` 的 `CandidateView.kt:139-142`），**没有任何 touch-slop 判定**（`grep -ci slop` 两棵树都是 0）。Android `View` 的点击只看 UP 落点是否还在自身边界内（`pointInView` 还外扩一个 slop），中途位移不参与判定。几何上正好对上实测：候选内容带实测 105 px（= 38.2 dp，见 §5 可访问性表），加一个 slop 22 px → 有效命中框 ≈127 px ≈ 整条带高 125 px，所以**「落点不出带」≈「落点不出项」≈ 触发点击**；dy ≥ 110 出带即出框，才不上屏。这同时解释了 AC-7 的 200 px 那一档为什么一直是绿的 —— **它测的正好是不触发的那一半，触发的这一半此前不在任何 AC 的判据面里。**

**是否本次变更引入：不是。** `fa57a07`（main）与 `c524351`（PR #18 head）同一段代码、同一行为 → 属既有债。按 PM 11-16 对 §9.4/§9.5 的先例：**不计入 PR #18 拦路面，VOCA-47 本单不判 FAIL**，也不占用打回项 1 的重测批次。

```
Given  同 AC-4（候选条可见、候选池 ≥ 8），候选带偏移为 0
When   在候选带内做近垂直拖动：|dx| < 8 dp（touch slop），起手点 = 带顶 + 14 dp（@440dpi y=1391，与 ev_vswipe_a 同口径），
       dy ∈ {20, 40, 60, 80} px @440dpi（= 7.3 / 14.5 / 21.8 / 29.1 dp，520 dpi 按 dp 换算取整），dur 120 ms，落点仍在候选带内
Then   宿主文本域内容不变（不上屏）
And    候选带位移 = 0 px，IME 窗口在位（不得因为这次手势把键盘收掉）
```

> 阈值只到「观察到的 80 / 110 之间」，本轮未细分，所以判据取 dp 表达的一档覆盖已观测窗口并留余量，**不猜常量**。

**修复口径（建议，具体实现由 Stage 2 选）**：候选项点击加 touch-slop 约束 —— UP 相对 DOWN 的位移 > `ViewConfiguration.getScaledTouchSlop()`（8 dp：440 dpi 22 px / 520 dpi 26 px）时不触发上屏，横滚仍由 `HorizontalScrollView` 抢占。它不动恒高、不动 G1–G7，也不与 AC-4「禁止用触摸滑动位移做判据」冲突：AC-4 判的是「滚了多少」（不可复现），本条判的是「有没有多打出一个字」（宿主文本真值，可复现）。

**对照物缺口（标注待确认，不影响裁决）**：搜狗 / Gboard 同口径下会不会上屏，本轮未测（§1.2 的旧结论就是「不依赖对照物」）。本条的依据是「未定义手势不得有副作用」，不是「别人也这样」。

**处置**：立为 `spec-AC11`，VOCA-47 本轮不测；建议新开 issue（P2，既有债）交 Stage 2，判定式即本条，与 §5 的「候选词可点高度 ≥48 dp」同批修最省（同一处触摸与尺寸改动）。

**无障碍子用例（随本条一起补，不阻塞裁决）**：TalkBack 开启（`isTouchExplorationEnabled`）时重复同一手势 —— 期望同样不上屏，且**正常点选（双击激活候选项）仍然可用**。触摸探索走的是无障碍节点激活路径、不吃 `View` 的 UP 落点判定，所以 F12 对读屏用户不成立；这一档是防止修复把读屏用户的点选一起削掉。

## 5. 不可访问性检查（无障碍）

| 检查项 | 结论 | 依据 / 处置 |
|---|---|---|

## 6. 占屏收敛：组件级方案

### 6.1 目标（按 `fa57a07` 重测数字重算，**模拟器口径**）

> **口径**：本节与 §6.2 的 px / dp / pp 全部换算基于 `emulator-5554`（1080×2340、density 440、`font_scale` 1.0），**不是目标设备结论**。判定式（相对搜狗 ≤ 1 pp、Δ=0）与方案排序与设备无关，但**绝对值与 pp 结论必须在真机复跑后定稿**（§9.1）—— 真机 1260×2720 / 520 dpi / `font_scale` 1.15，分母与字号缩放都不同，`+0.46 pp` 这种小数位结论换设备会翻。

搜狗 **978 px / 355.6 dp（41.79 %）**。门限「相对搜狗 ≤ 1 个百分点」= 上限 **1001 px / 364.0 dp**（本机 1 pp = 23.4 px = 8.51 dp）。
现状组合态 **1056 px** → 需要砍掉 **≥ 55 px = 20.0 dp**。

换算模型（由 §1.4 实测带直接得出，不是拟合）：

```
总高 = 候选条 + 工具栏块 + 键区 4 行 + 底部块
     = 46 + 49.5 + 4 × (键高 + 2 × keyMargin) + 48      [dp]
自检：46.5 + 49.5 + 4 × (52 + 4 + 4) + 48 = 384.0 dp = 1056 px ✓ 与实测 frame 完全相等
```

**每压 1 dp 键高 = 省 4 dp 总高**（4 行），所以 52 → 46 一次省 24 dp = 66 px，是全部手段里性价比最高的一条。

- 只动两个数：候选条恒高（一行 XML）+ 键高档位默认值 `STANDARD → COMPACT`（`KeyboardSettings.kt:4-7` 的 `enum class KeyboardSize`，`COMPACT("紧凑", 46)` 已存在，**不需要新增档位**）。

- **B2 的 `keyMargin 3` 前提已经失效**（`07214d6` 回退，见 §1.4），旧版本节把它当作 main 现状来算 +0.11 pp 是错的；按现状重算，压到 3 反而过冲 0.71 pp，还会让键间距从 11 px 掉到 8 px（粘连感）。

### 6.3 方案对照

| | A 只钉恒高 | **B1 恒高 + 压键高（推荐）** | B2 再压 keyMargin | D 合并单条 |
|---|---|---|---|---|
| 消掉 +6 px 跳动（AC-1） | ✅ | ✅ | ✅ | ✅ |
| 达到 ≤ +1 pp | ❌ +3.28 | ✅ **+0.46** | ✅ −0.71（过冲） | ✅ −4.89（过冲更多） |
| 改动面 | 1 行 XML | 1 行 XML + 1 个默认值 | + 键间距观感变化 | 大（工具栏 8 个入口与候选混排） |
| 需人类确认 | 已确认（§7.1 #3） | 已确认 | **否**（前提已回退） | 是 |

### 6.4 不建议的做法

- **只钉恒高、不压键高（方案 A）**：AC-1 过了，但占屏仍 +3.28 pp，本 issue 的收敛目标没达成。
- **把 `keyMargin` 压到 3（方案 B2）**：`07214d6` 已经把它从 3 回退到 4，再压一次等于推翻别人的 UI 决定，且换算后过冲 0.71 pp。要做先开 issue 找 UI，不在本规格里定。
- **按旧 1092 / 985 px 做收敛计算**：那两个数字对应的两行候选条与 `keyMargin 3` 都已不在 main 上，照它们算出来的「+0.11 pp」不可复现。
- **缩小候选条高度到 44 dp 以下**：候选内容行实测 38.2 dp（`scrollView minHeight 38dp`）+ 上下 padding 8 dp = 46 dp，再压会截字；真机 `font_scale=1.15` 下截得更明显。

### 8.3 组件拆解（整行均匀度判定边界，规避 `#F2F3F5` 同色问题）

```bash
$ADB exec-out screencap -p > shot.png
```

**方法**：不用「取某个像素的颜色」判断组件边界 —— 候选条、工具栏、键区底色几乎同色，取色分不开。改用**同行均匀度**：

1. 对区间内每一行，在 x 方向等距采 12 个点；
2. 若 12 点同色，该行视为「纯背景行」；若不同色，视为「有内容行（键/文字/图标）」；
3. 连续的有内容行 / 纯背景行即构成一个组件带；
4. 用 `dp = px / 2.75`（本轮 density 440；真机是 `/ 3.25`）换算，与 frame 高度对账。

本文件 §1.4 的组件带数字都由这个流程得出，自检式：**各带高度之和必须等于 frame 高度**（实测 `128 + 136 + 660 + 132 = 1056` ✓）。

### 8.4 横滚位移与边界（列剖面互相关，AC-4～AC-7 的取数）

```bash
$ADB exec-out screencap -p > before.png
$ADB shell input keyevent 70            # KEYCODE_EQUALS，一次 72 dp
sleep 0.5
$ADB exec-out screencap -p > after.png
$ADB shell uiautomator dump /sdcard/ui.xml && $ADB shell cat /sdcard/ui.xml   # 宿主文本真值
```

**位移怎么算**：取候选带（本轮 `y=1284–1411`，换设备按 §8.3 重取）全宽，按 x 每 2 px 采样一次灰度均值，得到剖面 `P(x)`；对 `before`/`after` 两个剖面在 `−600…+600 px` 范围内做滑动互相关，取绝对误差最小的偏移 `s` —— `s > 0` 表示内容向左滚（看到更后面的候选）。同时报告残差（`mean|P_after(x+s) − P_before(x)|`），**残差 > 5 视为「不是同一段候选」，判定作废重测**（防止把「候选集变了」误读成「滚了」）。

**为什么必须配一个「宿主文本不变」的对照**：滚动和上屏在截图上可能长得一样（候选区都变了）。只有 `uiautomator` 读到的 focused `EditText` 文本不变，才能证明这次变化是浏览而不是提交。注意 IME 窗口自身**不可 dump**（`uiautomator dump` 只给宿主窗口节点），所以候选内容只能靠像素，宿主文本只能靠 dump —— 两条合起来才是完整判据。

**触摸滑动不要用来做定量判定**：`input swipe` 带 fling，实测手指 100/200/400/600 px → 实际滚动 94/256/380/330 px（非单调，§2.3 F5）。触摸用例只用于判定「不该动的没动」（AC-6/AC-7）。
