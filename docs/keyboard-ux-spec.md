# 键盘交互规格（VOCA-37 Stage 1）

本文件是 VOCA-45 的交付物，覆盖 VOCA-37「输入法用户体验优化」Stage 1 的交互规格。
**只出规格，不含实现代码**；代码归 Stage 2（VOCA-46）。

- 适用基线：`f3df320`（本分支起点），并以 **VOCA-30 合并后的目标态** 为尺寸基准。
- 量测设备：真机 `FMR0224913042917`（ALN-AL00 / 1260×2720 / density 520 → 3.25 px/dp）。
- 量测时间：2026-11-09。
- 本文件中的每个「实测」都附了取数方式；测不到的写「未测到」，不写推测。

---

## 0. 结论速览

| # | 项 | 采纳 | 一句话规格 |
|---|---|---|---|
| 1 | 候选条空态 | **采纳（改语义）** | 空候选时候选条不消失，改为**恒定高度**：不随空态/组合态变化，消掉键盘跳动 |
| 2 | 双击空格出句号 | **采纳（默认关）** | 仅在「无组合、无联想、无面板、光标后是正文或行尾」时生效；时间窗 300 ms。搜狗 11.36 **出厂 `space_double_click_as_period = false` 已实测确认**（模拟器 `pm clear` 后直读 MMKV 字节 `01 00`） |
| 3 | 候选条滑动翻页 | **采纳** | 水平位移 ≥ 40dp 且水平位移 > 垂直位移 × 1.5 时翻一页；起手必须落在候选词区。阈值与搜狗无关（搜狗侧未证实），见 §1.2 |
| 4 | 按键音效 | **不采纳（本期）** | 依赖新增音频资源与系统「触摸提示音」联动，收益低于成本；只补规格不做实现，理由见 §4 |
| 5 | 键盘手势删除（左滑退格） | **不采纳（本期）** | 与候选条水平滑动、以及输入法手势导航区的系统返回手势冲突面过大 |

占屏高：现状 **1092 px（40.15 %）**，组合中会涨到 **1196 px（43.97 %）**；搜狗 **985 px（36.21 %）**且组合中不变。
收敛方案见 §6，推荐 **方案 B2** = 候选条改单行（消掉跳动）+ 合并 VOCA-30 的 `keyMargin 3` + 键高 46dp，得 **988 px（36.32 %）**，相对搜狗 **+0.11 pp**，在「≤ +1 pp」门限内。
注意：**只压键高不够**；保留两行只钉高度也不够（§6.2 已用表格证明不可达）。候选条改单行是必须项。

## 1. 实测证据（本轮新增，PM 交办的三件事）

### 1.1 双击空格：搜狗不输出句号

真机 `FMR0224913042917`，搜狗输入法，记事本 `notetext_textview`，用 `uiautomator dump` 读文本域真值：

| 输入法 | 前置状态 | 间隔 | 结果文本 | 判定 |
|---|---|---|---|---|
| 搜狗 | 空缓冲 | 150 ms | `'  '`（两个空格） | 无句号 |
| 搜狗 | 空缓冲 | 400 ms | `'  '` | 无句号 |

搜狗确实**有**这个功能，但**默认关闭**，且存在三个独立开关：

- 文案「双击空格添加句号」（`aapt2 dump strings` 命中 `string/b3k` 附近的「按键音效」同组资源）。
- 存储键：`space_double_click_as_period`、`space_double_click_as_period_en_nine`、`space_double_click_as_period_en_pro`。
- 真值存储位置：`/data/data/com.sohu.inputmethod.sogou/files/mmkv/com.sohu.inputmethod.sogou.foreign_settings`（MMKV，**不是** `shared_prefs`）。
  实测字节：键名后紧跟 `01 00`，即 bool=`false`（偏移 692）。`shared_prefs` 里根本没有这个键 —— 之前往 `shared_prefs` 注入无效，原因就在这里。

> **第二轮复核（2026-11-10，模拟器 `emulator-5554`，root）**，把开关与效果彻底分开，修正上一轮的测量瑕疵：
>
> 1. **出厂值 = 关（硬证据）**：`pm clear com.sohu.inputmethod.sogou` 后直读 `foreign_settings`，键名后字节为 `01 00`，即 `bool=false`；`shared_prefs` 里没有该键。上一轮读到的 `01 01` 是被人为改过之后的状态，不是出厂态。
> 2. **写入 true 后仍不出句号**：先 `am force-stop` 再 `dd` 写盘（避免 MMKV 内存副本回写覆盖），复查字节确为 `01 01`，重启搜狗后重测：间隔 100/200/300/450/700 ms × 「空缓冲直出」与「拼音组合中」两态，**全部只得到两个半角空格，无 `。` 也无 `.`**；三连击得到三个空格。
> 3. **测试通道限制（必须标注）**：本轮用 `input keyevent 62` 而非触摸点击 —— 搜狗键盘是自绘 View（窗口 `fillxfill`、无 uiautomator 节点），坐标法在该模拟器上反复漂移，落键自证不通过。`keyevent` 与真实触摸在 `handleSpace()` 侧是否等价**未验证**。因此「开启后不出句号」这条的强度低于「出厂默认关」那条。
>
> **净结论（不变）**：搜狗 11.36 开箱不给句号。规格里的 300 ms 仍是自定值。

### 1.2 候选条滑动翻页：结论不确定，按「不依赖它」处理

这一条我**没能拿到干净证据**，如实写清楚，不编结论。

真机（`FMR0224913042917`）单次观察：

- 在候选条内水平滑动 `1000→600`（400 px / 123 dp）后，候选列表签名改变、组合码不变、文本域不变 → 当时判为「翻页成立」。

但在受控复测中这个结论**不成立**：

| 环境 | 用例 | 结果 |
|---|---|---|
| 真机 | 多次受控扫描（不同距离、加 0px 点击对照） | 每个手势（含纯点击）都会改变候选区签名 → 度量本身无效 |
| 模拟器 `emulator-5554` | 条内左滑 400 px | 候选变、组合码变、**文本变** → 是**上屏候选**，不是翻页 |
| 模拟器 | 条内右滑 400 px / 0px 点击 / 条外滑动 / 键区滑动 / 条内左滑 150 px | 全部无变化 |

结论：**搜狗 11.36 在实测环境里没有表现出可靠的「候选条横滑翻页」行为**；唯一能复现的效果是「滑动被当成点击上屏了候选」。

**第二轮复核（2026-11-10，模拟器，冷启动 + 出厂态）** 补了两条量化数据：

| 用例 | 结果 |
|---|---|
| 候选带内 `y=1500` 左滑 800 px（300 ms）| 候选区像素哈希 `7b9ab345e953` → `7b9ab345e953`，**未变** |
| 硬件翻页键 `KEYCODE_EQUALS`（搜狗「减号等号」翻页方案）| 同一哈希，**未变** |

第二条尤其关键：连**专用翻页键**都不改变候选区，说明当时并不存在「可翻的候选页」（候选条为空或只有一页），而不是「滑动没被识别」。这也解释了第一轮「有时变、有时不变」的抖动 —— 变化来自候选条自身的动画/时钟，不是翻页。

因此本规格**不把「对齐搜狗」当作翻页的依据**，改为按我们自己的可用性需求定义（§2.3），并在 §9 明确标注搜狗侧未证实。这是刻意选择：宁可给一个我们自己论证过的阈值，也不抄一个没测准的数。

### 1.3 按键音效：搜狗有开关，默认关

搜狗 11.36 的 `shared_prefs/com.sohu.inputmethod.sogou_preferences.xml`（模拟器 root 直读）：

```xml
<boolean name="keyboardfeedback_volume_switch" value="false" />
<boolean name="keyboardfeedback_vibration_switch" value="false" />
<boolean name="pref_keyboardfeedback_linear_motor_vibration_switch" value="false" />
<boolean name="pref_use_talkback_keyboard_specal_vibrate" value="true" />
<int     name="pref_vibrate_value_keyboard_feedback" value="5" />
```

- 按键音开关 **默认 false**；按键振动 **默认 false**；TalkBack 专用振动 **默认 true**。
- 文案里有「无障碍模式下，我们会为您自动开启按键音和按键振动」—— 即音效的启用条件是**无障碍模式**，不是普通模式。
- 真机侧 `settings get system sound_effects_enabled` = **0**（系统触摸提示音关闭）。
- 未测到：真机（无 root）上打开音效后的实际播放行为，因搜狗设置页在真机上无法稳定进入。**不推测波形/音量**。

**第二轮复核（2026-11-10，模拟器，root）** —— 把「测不出来」的原因查清了，不是方法问题：

| 检查 | 结果 | 含义 |
|---|---|---|
| 系统 UI 音效资源 | `/product/media/audio/ui/` 有 24 个文件，含 `KeypressSpacebar.ogg`、`KeypressStandard.ogg` | 系统侧资源**齐全**，排除「没资源可放」 |
| `settings system sound_effects_enabled` | 改 `1` 后复读仍为 `1`，但按键**仍无任何音频事件** | 开关不是唯一前置条件 |
| `dumpsys media.audio_flinger` track 计数 | 按键 6 次：`28463 → 28461`（-2，噪声级） | **无新建 track** |
| 阳性对照：`input keyevent 24`（音量键，系统必响） | `af_len` 仅 +157 字节（dumpsys 文本抖动），track 数 `0 → 0` | **阳性对照失败** |

阳性对照失败是关键：连系统保证会发声的音量键都测不到 track，说明这台 headless 模拟器**没有可用的音频输出后端**，任何「有声/无声」的判断都不成立。

> 所以音效这一项的性质是：**本环境物理上无法测量**，不是「测了没声」。结论只能是「未测到」，且**不得**据此写「搜狗按键无声」。

`product` 分区而非 `system` 分区也解释了一个容易踩的坑：在旧版 AOSP 镜像上 `/system/media/audio/ui` 不存在，按老路径检查会误判成「没有音效资源」。

### 1.4 键盘占屏：组件级拆解（PM 未完成的那一半）

`dumpsys window displays` 的 `mImeHeight` + 截图行带分析（`#F2F3F5` 同色问题用「整行是否均匀」判定，而不是取色）。下面每个数字都由像素带边界换算，`dp = px / 3.25`：

| 组件 | iSpeech | 搜狗 | 差 |
|---|---:|---:|---:|
| 顶部留白 | — | 58 px / 17.8 dp | — |
| 候选/工具条（搜狗单条） | — | 110 px / 33.8 dp | — |
| 条与键区之间的间隔 | — | 54 px / 16.6 dp | — |
| **chrome 小计（键盘顶部非键区）** | **312 px / 96.0 dp** | **222 px / 68.3 dp** | **+90 px / +27.7 dp** |
| 键区 4 行（含每行上下 `keyMargin`） | 780 px / 240.0 dp | 720 px / 221.5 dp | +60 px / +18.5 dp |
| 底部留白（键区之外独立占位） | 0 px / 0.0 dp | 42 px / 12.9 dp | −42 px / −12.9 dp |
| **合计** | **1092 px / 336.0 dp** | **985 px / 303.1 dp** | **+107 px / +32.9 dp** |

像素带边界（真机空态）：iSpeech `1628`（键盘顶）→ `1940`（首行键顶）→ `2720`（屏底）；搜狗 `1735` → `1957`（首行键顶）→ `2720`。

**建模说明**：iSpeech 底部那 14 px（4.3 dp）是第 4 行键的 `keyMargin`（4 dp ≈ 13 px），属于「行高」而不是独立的底部留白，所以计入键区 4 行；搜狗底部 42 px 是键区之外的独立留白。两边按同一口径切分后，差值三项相加 `90 + 60 − 42 = 108 px`，与实测总差 `107 px` 相差 1 px（取整误差）。

拆解结论：**多出来的 107 px，主要来自顶部 chrome（+90 px），不是键高（+60 px）** —— 而且底部留白还替我们省回了 42 px。
所以「压键高」单独做只能追回 60 px，**必须同时动顶部两行结构**才能收敛 —— 而顶部一改，方案可行性就变了（§6.2 表 A 证明「保留两行只钉高度」不可达）。

并且实测发现一个 PM 没测到的差异：

| 状态 | iSpeech | 搜狗 |
|---|---:|---:|
| 空候选（无组合） | 1092 px | 985 px |
| 组合中（有候选） | **1196 px（+104 px）** | 985 px（**不变**） |

**增量落在哪**（真机截图逐行比对，两种状态同一坐标）：

- 键区 4 行与底留白在两种状态下**像素位置完全一致**（首行键顶 `y=1940`、末行键底 `y=2303`、底留白 `2706–2719`）。
- 顶部「候选条 + 工具栏」区块从 `312 px`（`1628–1939`）涨到 `416 px`（`1524–1939`），**正好 +104 px**。
- 也就是：**组合时候选条自己长高，把整个键盘往上顶，键区一个像素都没动**。

**为什么会自己长高**（代码可解释）：`candidate_view.xml` 是**竖向两行**结构 ——

| 行 | 空态 | 组合态 |
|---|---|---|
| 第 1 行：组合码 `candidate_code`（`18sp`，上下 padding 2+2） | `GONE` | `VISIBLE` |
| 第 2 行：候选区（`minHeight 38dp`） | 候选区 `GONE`，仅翻页器/齿轮残留 | `VISIBLE`，`22sp` 文字 + 上下 padding 6+6 |

空态时两行都塌掉，只剩根布局的 `minHeight 44dp` + `padding 4+4`；组合态两行都撑起来。所以增量 = 组合码行 + 候选行的高度，且**由 `sp` 字号驱动**，随 `font_scale` 变化：

| 设备 | `font_scale` | 空态 | 组合态 | 增量 |
|---|---:|---:|---:|---:|
| 真机 `FMR0224913042917` | 1.15 | 1092 px | 1196 px | **+104 px = 32.0 dp** |
| 模拟器 `emulator-5554` | 1.0 | 990 px | 1084 px | **+94 px = 34.2 dp** |

两者像素增量不同、dp 增量也不同 —— 说明这不是一个固定 `dp` 常量，而是**文字行高耦合**出来的。这点很重要：**任何按 dp 静态凑数的方案都治不了它**，只能靠「候选条固定高度」从结构上消除。**这是「打字时键盘跳」的根因**，必须在 Stage 2 一起解决。

## 2. 五项交互规格

### 2.1 候选条空态

**触发**：`CandidateView.update()` 被调用且 `list.isEmpty()`（`CandidateView.kt:89` 起，当前在 `:103` 只 GONE 内部候选行，条自身常驻）。

**规格**：候选条改为「**单行 + 固定高度**」—— 组合码内联到同一行的最左侧，与候选词共处一行，高度钉死在**当前空态的 46 dp**（实测顶部 chrome 96 dp 中的候选条部分）。

| 状态 | 内容（同一行，从左到右） | 高度 |
|---|---|---|
| 空候选 | 组合码区留白 + 齿轮 | **46 dp，固定** |
| 有候选 | 组合码 + 候选词 + 翻页器 + 齿轮 | **46 dp，固定** |

**为什么必须是「单行」而不是「两行钉高」**（这是本轮最重要的推演，直接决定方案可行性）：

- 若保留现在的两行结构并钉死在组合态高度，候选条会从 46 dp 变成约 78 dp，顶部 chrome 从 **96 dp 涨到 128 dp**。
- 那么即使键高压到 46 dp、行距压到 3 dp，总高仍是 `128 + 208 = 336 dp = 1092 px`，**相对搜狗 +3.93 pp，目标彻底不可达**（详见 §6.2 表 A 组）。
- 只有「单行 + 钉在 46 dp」，才能同时满足「不跳」和「不增高」：chrome 恒为 96 dp，压键高后落到 `304 dp = 988 px`（§6.2 B 组）。

**实现约束**：

1. 组合码不再单独占一行，改为行内左侧的一个 `TextView`（`candidate_code`），`list.isEmpty()` 时 `text=""` 但**不 `GONE`**、不改变布局高度。
2. 根布局 `minHeight = 46dp`，并确保两态下的实际测量高度都等于 46 dp（不能用 `wrap_content` 让 22sp 文字把它撑高 —— 真机 `font_scale=1.15` 下 22sp 已是 25.3 dp，加 padding 就会超）。
3. `list.isEmpty()` 时只清 `itemContainer` 子 View，不动容器高度。

**理由**：候选条是**竖向两行**，且两行在空态都被 GONE 掉，这是 +104 px 跳动的直接来源（§1.4）。改单行是唯一既消跳动、又不增加常态高度的做法 —— 搜狗本身就是单条结构（110 px / 33.8 dp）。

**副作用（必须接受）**：组合码从独立一行变为与候选词同行，**横向空间变紧**。真机 1260 px 宽下，组合码约占 120 px，剩余给候选词 + 翻页器 + 齿轮。规格要求：候选区保持 `HorizontalScrollView` 横向滚动（已实现），并保证**至少完整显示 4 个候选**；不足时优先牺牲翻页器宽度而不是候选数。

**冲突与优先级**：
- 与「候选条空态收起」相反 —— 本规格明确选择常驻 + 恒高。
- 「候选条是否允许改成单行」属于**改默认观感**的产品取舍，**需人类确认**（§7 #1 已列）。

**状态覆盖**（输入态 × 候选态 × 面板态）：见 §3 矩阵。

### 2.2 双击空格出句号

**触发**：`handleSpace()`（`IspeechImeService.kt:713`）。

现有 `handleSpace()` 的优先级链条是：
`t9Digits` → `buffer` → `aiReplyActive` → `voiceActive` → `associationActive` → 直接输出空格。

**规格 —— 双击只在「链条走到底、且上一次上屏也是空格」时生效**：

```
space 按下:
  1. t9Digits 非空              → commitT9()            （不变）
  2. buffer 非空                → commitTop()           （不变）
  3. aiReplyActive              → commitAiReply()       （不变）
  4. voiceActive                → commitVoice()         （不变）
  5. associationActive          → pickCandidate(0)      （不变）
  6. 以上都不成立:
       if 距上次「空格上屏」≤ 300ms 且 中间无其他上屏/删除/移动光标:
           deleteSurroundingText(1,0)   # 删掉第一个空格
           commitText("。")              # 中文标点开启、非英文态
       else:
           commitDirect(" ") 并记录 lastSpaceCommitAt
```

**关键规则（必须有，否则会打架）**：

| 规则 | 内容 |
|---|---|
| R1 | 第二次按键的净效果是**「两个空格变成一个句号」**：先删掉已上屏的那一个空格，再上屏「。」。**不是**「两个空格后再补一个句号」。实现上对应 `deleteSurroundingText(1,0)` + `commitText("。")`，两步要放在同一次 `InputConnection` 编辑批次里，避免中间态被输入法/宿主看见。 |
| R2 | 判定窗口 **300 ms**（`DOUBLE_TAP_MS = 320L` 已存在于 `SoftKeyboardView`，规格取 300 ms 与之同量级；实现可复用该常量）。 |
| R3 | 任何**非空格**上屏（候选、标点、字母、语音、AI）都清零 `lastSpaceCommitAt`。 |
| R4 | 退格、移动光标、切换面板、切换输入法、切换中英，同样清零。 |
| R5 | 有候选时**永远先上屏首选**，双击逻辑不参与 —— 这是本条最重要的冲突点。用户连按两次空格想打句号，第一次就会把首选词上屏，第二次变成普通空格。 |
| R6 | `chinesePunctuation = false`（`app/src/main/java/com/ispeech/settings/store/KeyboardSettings.kt:21`，默认 `true`）或英文态（`mode == Mode.ENGLISH`）→ **不转换**，输出两个空格（对齐搜狗：搜狗英文态也不加句号）。 |
| R7 | 光标前一个字符已经是「。！？；」等句末标点时仍生效（不做智能判断），避免「有时灵有时不灵」。 |
| R8 | **不与空格长按语音冲突**：空格已绑 `installSpaceGesture`（`SoftKeyboardView.kt:626`，按住 500 ms 进语音，阈值来自设置 `voice_space_long_press_ms`）。双击是**两次独立点击**，每次点击的按住时长都远小于 500 ms，因此不会误触语音。规格要求：双击判定必须在服务侧 `handleSpace()` 做（已经如此），**不得**改成 View 层的双击手势，否则会与长按 runnable 抢事件。 |

**默认值**：**关闭**（`KeyboardSettings` 新增 `doubleSpacePeriod: Boolean = false`），设置页给开关「双击空格添加句号」。
理由：这是我们自己的新行为，默认开启会改变既有用户的手感；且搜狗自身也默认关闭。

### 2.3 候选条滑动翻页

**触发**：`CandidateView` 新增触摸处理（当前全文无 `GestureDetector` / `onFling`）。

**规格**：

| 项 | 值 | 依据 |
|---|---|---|
| 响应区域 | 仅候选词横向滚动区（`candidate_scroll` 的 bounds 内） | 我们自己的需求：避免与键区/面板抢手势 |
| 生效条件 | 有候选且 `pageCount > 1` | 单页时滑动应为 no-op |
| 触发阈值 | 水平位移 ≥ **40 dp**（真机 130 px） | **自定工程值**。候选条高约 44 dp、单个候选宽约 60–90 dp；40 dp 既能与「点选候选」拉开距离，又不至于要求长距离扫动。搜狗侧未测准（§1.2），不用它做依据 |
| 方向判定 | `abs(dx) > abs(dy) * 1.5` 才算水平手势 | 防止斜滑误判 |
| 位移方向 | 左滑（dx < 0）→ 下一页；右滑 → 上一页 | 与阅读方向一致（内容向左移出一个视口 = 前进） |
| 边界 | 首页右滑、末页左滑 → no-op，**不循环** | 循环会让用户失去位置感；与翻页器 `prev` 在首页置灰（`DISABLED_ALPHA`）的现有表现一致（`CandidateView.kt:115`） |
| 反馈 | 翻页成功时触发一次 `performHapticFeedback(VIRTUAL_KEY)`（受 `vibrate` 开关控制） | 与按键反馈一致 |

**冲突与优先级**：
- 与 `HorizontalScrollView` 自身的横向滚动冲突。规格要求：**先判翻页，再让滚动**。即手指抬起时若满足阈值 → 翻页并 `abortAnimation`；否则维持滚动位置。
- 与候选词点击冲突。规格：位移 < 8 dp 视为点击（沿用 Android `ViewConfiguration.getScaledTouchSlop()`），不做翻页。
- 与「长按候选记忆自造词」冲突。规格：**长按优先**，长按触发后本次手势不再判翻页。

**不做**：上下滑翻页（搜狗未测到，不发明）。

### 2.4 按键音效 —— 不采纳（本期）

**理由（按门禁要求写明，不静默丢项）**：

1. 搜狗自身的按键音**默认关闭**，且只在无障碍模式下自动开启（§1.3）。也就是说「对齐搜狗」的正确结论是**保持关闭**，而不是加音效。
2. 实现需要引入音频资源（`res/raw/*.ogg`），会增大 APK；且必须正确处理 `Settings.System.SOUND_EFFECTS_ENABLED` 与静音/勿扰模式，否则会出现「静音了还响」的严重缺陷。
3. 真机上无法验证播放效果（无 root、搜狗设置页进不去），按门禁「无实测证据不写规格」的原则，只能标未测到。

**本期替代**：维持现有 `performHapticFeedback(VIRTUAL_KEY)`（`SoftKeyboardView.kt:770`），并在设置页把「按键震动」开关的默认值与说明文案补齐。
若后续人类明确要求音效，建议新开 issue，规格要点：默认关、跟随系统 `sound_effects_enabled`、勿扰模式静音、音量取 `AudioManager.FX_KEY_CLICK`。

---

### 2.5 键盘手势删除（左滑退格）—— 不采纳（本期）

**理由**：

1. 与 §2.3 的候选条水平滑动**在同一方向上抢手势**，两个都做会让用户无法预测结果。
2. 键盘区域紧贴屏幕底部，正是 Android 手势导航的「返回」热区；在键面上做左滑会与系统返回手势冲突，且我们无法可靠区分（`View` 层拿不到系统手势的拦截结果）。
3. 搜狗的实现落在**删除键自身**（长按连删 + 滑动），而不是「键盘任意位置左滑」。这个我们**已经实现**（`startRepeatDelete()`，`SoftKeyboardView.kt:776`），所以「手势删除」的真实缺口并不存在。

**保留项**：长按删除键连续退格（现状已实现，规格要求保留 `REPEAT_START_DELAY_MS=380 / SLOW=90 / FAST=45`）。

## 4. 可测验收标准（Given / When / Then）

每条都能被 `adb` 或单测判定，不含「流畅」「自然」这类词。

### AC-1 候选条空态高度不变

```
Given  设备已设 iSpeech 为默认输入法，任一文本编辑器获得焦点，键盘已弹出
When   记录 mImeHeight（空候选），然后输入 4 个字母形成组合，再记录 mImeHeight
Then   两次 mImeHeight 的差值必须为 0
```

当前实测（真机 `FMR0224913042917`）：`1092 → 1196`，**差 +104，本项不通过**。
模拟器 `emulator-5554` 同样不通过：`990 → 1084`，差 +94。

> 判定只看**差值**，不看绝对值 —— 不同设备/密度/nav bar 下的绝对值本来就不同。

### AC-2 双击空格出句号

```
Given  中文五笔态、无组合、无联想、中文标点开启、双击空格开关开启
When   在 300ms 内连按两次空格键
Then   文本域内容为 "。"（不是 "  "），且长度为 1
```

对照（同条件把开关关闭）：
```
Then   文本域内容为 "  "，长度为 2
```

### AC-3 双击空格不与「上屏首选」打架

```
Given  中文五笔态、已输入组合码且有候选、双击空格开关开启
When   在 300ms 内连按两次空格
Then   第一次空格上屏首选词，第二次空格输出一个普通空格
And    文本域中不出现 "。"
```

### AC-4 滑动翻页生效

```
Given  候选多于一页（pageCount > 1）
When   在候选词区从 (x=900,y=条中心) 水平滑到 (x=400,y=条中心)，耗时 200ms
Then   候选列表内容改变，且当前组合码不变
And    翻页指示器由 "1/N" 变为 "2/N"
```

### AC-5 滑动翻页的边界

```
Given  当前在候选第 1 页（pageCount > 1）
When   在候选词区向右滑 200dp
Then   候选列表不变，页码仍为 "1/N"，且不触发候选上屏
```

### AC-6 起手区约束

```
Given  候选多于一页
When   在键盘按键区（非候选条）水平滑动 200dp
Then   候选页不变（该手势被按键处理，不是翻页）
```

### AC-7 竖向滑动不误翻

```
Given  候选多于一页
When   在候选条内竖向滑动 200dp
Then   候选页不变
```

### AC-8 按键音效（本期不采纳，无验收项）

标注：**N/A**。若后续采纳，验收为「系统 `sound_effects_enabled=0` 时按键无声音」。

### AC-9 长按连删保留

```
Given  任意输入态
When   按住退格键 1.5 秒
Then   文本域被删除的字符数 > 3（证明连删生效）
```

## 5. 不可访问性检查（无障碍）

| 检查项 | 结论 | 依据 / 处置 |
|---|---|---|
| 双击空格 vs TalkBack 双击激活 | **不冲突** | TalkBack 的双击是「激活焦点元素」，作用在无障碍节点上；空格键是键盘视图的内部 `onKey` 回调，启用 TalkBack 时键盘整体会被 `SoftKeyboardView` 的按键视图接管。前提：双击逻辑**只挂在空格键的 key 回调**上，不做全局手势监听。 |
| 300 ms 时间窗 vs 无障碍「按键重复延迟」 | **需放宽** | 启用无障碍后系统会拉长按键接受间隔。规格：`AccessibilityManager.isEnabled` 为 true 时，窗口从 300 ms 放宽到 **600 ms**，并在设置页开关旁标注「无障碍模式下判定时间更长」。 |
| 滑动翻页 vs TalkBack 的滑动导航 | **需禁用** | TalkBack 开启时，单指滑动用于移动焦点。规格：`accessibilityManager.isTouchExplorationEnabled` 为 true 时**关闭候选条滑动翻页**，只保留翻页器按钮（`contentDescription` 已存在：上一页/下一页/页码）。 |
| 翻页器可点面积 | **不合规，需补** | `candidate_page_prev/next` 为 `wrap_content` + 上下各 4dp padding，按 24dp 图标推算可点高度约 **32dp**（`candidate_view.xml:65-107`），低于 48dp。规格：补 `minWidth/minHeight = 48dp`（WCAG 2.2 AA / Material 最小触控目标）。 |
| 候选词朗读 | **合规** | 每个候选 `contentDescription = candidate.display`（`CandidateView.kt:145`）。 |
| 键盘按键朗读 | **部分合规，需补** | 文字键靠 `TextView.text` 朗读（`SoftKeyboardView.kt:494-502` 的 `text = when {...}` 分支），图标键有 `contentDescription = keyLabel(...)`（`SoftKeyboardView.kt:456`）。缺口是**退格键**：键面文案是符号 `⌫`（`KeyboardLayouts.kt:73`），TalkBack 读不出语义。规格：`BACKSPACE` 用 `contentDescription = "删除"`。 |
| 动效可关闭 | **不适用** | 本期无新增动画；键盘无入场动画。 |
| 对比度 | **不合规（首选高亮）** | 计算值：组合码/正文 `#000000` on `#F2F3F5` = **18.91:1** ✅；首选高亮 `#FF6A00`（`CandidateView.kt:181`）on `#F2F3F5` = **2.59:1** ❌（正文要求 4.5:1；22sp 加粗也不够「大文本」豁免的 3:1）。规格：首选改为「正常色 + 加粗 + 底色胶囊」而非纯橙色字；具体色值交 UI 出令牌，UX 只给约束「≥ 4.5:1，且与普通候选有非颜色差异」。 |

**门禁结论**：§2.2 与 §2.3 均**可以**在补齐上表四项（无障碍放宽窗口、TalkBack 关闭滑动、退格/回车补 `contentDescription`、翻页器补 48dp 可点面积）后进入 Stage 2；未补齐前不得标记开发完成。对比度一项单独交 UI（`#FF6A00` 需换令牌），不阻塞交互实现。

## 6. 占屏收敛：组件级方案

### 6.1 目标

搜狗 985 px（36.21 %）。「相对搜狗 ≤ 1 个百分点」= 上限 **1012 px / 311.4 dp**（1 pp = 27.2 px = 8.37 dp）。

### 6.2 三个方案（含可行性判定）

三个方案都**先满足 §2.1 的前置**：候选条必须恒高，否则任何静态高度都会被组合态打破。

**方案 A：候选条保持两行，钉死在组合态高度**

把现在的两行结构保留，只把高度钉死（不 GONE），消除跳动。

| keyMargin | 键高 | chrome | 键区 | 合计 | 占屏 | 相对搜狗 | 判定 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 3 | 46 | 128 dp | 208 dp | 336.0 dp / 1092 px | 40.15 % | +3.93 pp | ❌ 不可达 |
| 3 | 52 | 128 dp | 232 dp | 360.0 dp / 1170 px | 43.01 % | +6.80 pp | ❌ |
| 2 | 46 | 128 dp | 200 dp | 328.0 dp / 1066 px | 39.19 % | +2.98 pp | ❌ |

**结论：方案 A 不可行。** chrome 钉在 128 dp 后，即使键高压到 46、行距压到 2，仍然是 +2.98 pp，离 +1 pp 差三倍。**「保留两行 + 只钉高度」这条路走不通** —— 这是本轮推演推翻的一个直觉上很合理的方案，写在这里避免 Stage 2 重走。

**方案 B：候选条改单行 + 压键高（推荐 B2）**

按 §2.1 把候选条改成单行（组合码内联），chrome 保持 **96 dp**，再压键高。

| keyMargin | 键高 | chrome | 键区 | 合计 | 占屏 | 相对搜狗 | 判定 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 4（现状） | 52 | 96 dp | 240 dp | 336.0 dp / 1092 px | 40.15 % | +3.93 pp | 基线 |
| 4 | 46 | 96 dp | 216 dp | 312.0 dp / 1014 px | 37.28 % | +1.07 pp | ❌ 差一点 |
| 3（VOCA-30） | 52 | 96 dp | 232 dp | 328.0 dp / 1066 px | 39.19 % | +2.98 pp | ❌ |
| **3（VOCA-30）** | **46** | **96 dp** | **208 dp** | **304.0 dp / 988 px** | **36.32 %** | **+0.11 pp** | ✅ **推荐** |

**推荐：B2 = §2.1 单行候选条 + VOCA-30 的 `keyMargin 3` + 键高 46 dp。**

**方案 C：候选条与工具栏合并成一条**

把候选条和工具栏（现在各 46 dp）合并成搜狗式一条，chrome 压到约 50 dp。

| keyMargin | 键高 | chrome | 键区 | 合计 | 占屏 | 相对搜狗 | 判定 |
|---:|---:|---:|---:|---:|---:|---:|---|
| 3 | 46 | 50 dp | 208 dp | 258.0 dp / 838.5 px | 30.83 % | −5.39 pp | ✅ 但过小 |
| 3 | 52 | 50 dp | 232 dp | 282.0 dp / 916.5 px | 33.69 % | −2.52 pp | ✅ 但过小 |

**不推荐**：比搜狗还矮 5 pp，键盘会显得局促；且合并后工具栏 8 个入口 + 候选词挤一行，可用性明显下降。仅作为「如果人类要求尽量小」的备选。

### 6.3 三方案对照

| | A 两行钉高 | **B2 单行+压键高（推荐）** | C 合并单条 |
|---|---|---|---|
| 消掉 +104 px 跳动 | ✅ | ✅ | ✅ |
| 达到 ≤ +1 pp | ❌ +3.93 | ✅ **+0.11** | ✅ −5.39 |
| 改默认观感幅度 | 小 | **中**（组合码挪行） | 大（工具栏与候选混排） |
| 回归面 | 小 | 中（`candidate_view.xml` + `CandidateView.kt`） | 大 |
| 需人类确认 | 是 | **是** | 是 |

### 6.4 不建议的做法

- **只压键高、不动候选条**：能省 60 px，但组合时仍会 +104 px 跳动，AC-1 不过。
- **保留两行只钉高度（方案 A）**：数学上不可达（见上表）。
- **单独压底部留白**：`keyMargin` 同时控制行距与底留白，压它会连带压掉键间距，键与键会粘连。
- **缩小候选条 `minHeight 44dp`**：候选字号 22sp 在 `font_scale=1.15` 下已是 25.3 dp，加 padding 12 dp 已超 38 dp 候选行高，再压会截字。

### 8.3 组件拆解（整行均匀度判定边界，规避 `#F2F3F5` 同色问题）

```bash
$ADB exec-out screencap -p > shot.png
```

**方法**：不用「取某个像素的颜色」判断组件边界 —— 候选条、工具栏、键区底色都是 `#F2F3F5`，取色分不开。改用**同行均匀度**：

1. 对区间内每一行，在 x 方向等距采 12 个点；
2. 若 12 点同色，该行视为「纯背景行」；若不同色，视为「有内容行（键/文字/图标）」；
3. 连续的有内容行 / 纯背景行即构成一个组件带；
4. 用 `dp = px / 3.25`（本机 density 520）换算，与 `mImeHeight` 对账。

本文件 §1.4 的所有组件数字都由这个流程得出，`mImeHeight` 与「各带高度之和」必须相等（实测 1092 = 1092，可作自检）。

## 9. 未测到 / 已知缺口

> **设备状态说明（2026-11-10 复核）**：真机 ALN-AL00（`FMR0224913042917`）在 USB 总线上可见，但只暴露两类接口 —— 厂商类 `255/255/0`（MTP）与大容量存储 `8/6/80`，**没有 ADB 接口 `255/66/1`**。即手机侧 USB 调试未开启，`adb devices` 全程为空。复核末段该设备已从 USB 总线消失。以下所有"模拟器"结论都来自 `emulator-5554`（Android 14，root），不是真机。

1. **搜狗开启「双击空格添加句号」后的真实时间窗**：出厂值已确认为 `false`（§1.1）。写入 `true` 后（`force-stop` + `dd` 落盘 + 复查字节）在 100/200/300/450/700 ms 五档、直出/组合两态下**仍未出现句号**，但该轮用的是 `keyevent` 通道而非触摸，与真实触摸是否等价未验证。本规格的 300 ms 是**自定值**，不是抄搜狗。
2. **搜狗候选条横滑翻页**：受控复测未能复现稳定翻页（§1.2），且同轮 `KEYCODE_EQUALS` 专用翻页键也不改变候选区 —— 当时无「可翻的页」。因此本规格的 40 dp 阈值与左右方向都是**自定**的，不是对齐搜狗。若后续确认搜狗确有该行为及其阈值，应回来更新本表并复跑 AC-4～AC-7。
3. **按键音效播放行为**：本环境**物理上不可测**（§1.3）。headless 模拟器的音频后端不产生任何 track，连音量键的阳性对照都失败；真机 USB 调试未开启、无法接入。**不得**据此写「搜狗按键无声」。
4. **真机全程未能接入**：USB 枚举成功但无 ADB 接口，`adb devices` 为空；复核末段设备从总线消失。§2.3 的边界用例（AC-5/AC-7）**未在真机上跑过**，仅用模拟器与既有截图验证。
5. **键盘坐标法在本模拟器上不可用**：搜狗键盘是自绘 View（窗口 `fillxfill`、uiautomator 无节点、键盘顶边随输入场景变化），逐点落键自证多次失败，期间还发生过 IME 被 `com.ispeech.ime` 抢回。所有依赖坐标的结论都只用像素/哈希做旁证，不作主证。
6. **VOCA-30 尚未合并**，§6 里「VOCA-30 合并后」的数字是**按代码常量推算**，不是设备实测；合并后需按 AC-1 重测并更新本文件。
