# Design

## Context

iSpeech 是一个 Android Kotlin 输入法应用，当前缺乏统一的质量保障体系。需要建立一套业界标准的 harness 规则来确保代码质量、性能和安全性。设计需要考虑现有项目结构（IME 服务、候选词视图、键盘布局等）和 Android 平台约束。

## Goals / Non-Goals

**Goals:**
- 建立可扩展的 harness 规则体系，支持未来功能的测试和质量保障
- 确保 harness 规则与现有开发流程无缝集成
- 提供清晰的文档和工具支持，降低团队采用门槛
- 实现渐进式采用，不影响现有开发节奏

**Non-Goals:**
- 重构现有代码逻辑（除非必要）
- 替换现有的构建系统（Gradle）
- 添加新的第三方依赖（除非绝对必要）
- 实现完整的自动化安全扫描（仅定义要求）

## Decisions

### 测试框架选择
选择 AndroidX Test + JUnit 5 作为核心测试框架，因为：
- 官方支持最佳，兼容所有 Android 版本
- 与现有 Gradle 构建系统无缝集成
- 社区支持广泛，文档丰富
- 替代方案（如 Espresso 单独使用）会增加复杂性且不必要

### 性能监控方案
使用 Android Profiler + 自定义性能监控模块，因为：
- 可以精确测量 IME 关键路径（按键处理、候选词生成）
- 不需要额外的第三方 SDK
- 可以与现有日志系统集成
- 替代方案（如 Firebase Performance Monitoring）会引入不必要的网络请求

### 安全实现方案
使用 Android Keystore + AES-GCM 加密本地数据，因为：
- 提供硬件级安全保护
- Android 官方推荐的安全存储方案
- 无需额外权限
- 替代方案（自定义加密）会增加安全风险

### 开发流程集成
集成 GitHub Actions CI/CD 流水线，因为：
- 与现有 GitHub 仓库无缝集成
- 免费且易于配置
- 支持 Android 模拟器测试
- 替代方案（Jenkins 或 GitLab CI）会增加运维复杂性

## Risks / Trade-offs

[测试覆盖率目标过高] → 从 80% 开始，根据团队反馈逐步提升到 90%
[性能监控开销] → 在调试版本中启用，在发布版本中禁用性能监控
[安全加密性能影响] → 使用硬件加速的 AES-GCM，性能影响可忽略
[CI/CD 配置复杂性] → 提供详细的配置文档和模板，降低学习成本
