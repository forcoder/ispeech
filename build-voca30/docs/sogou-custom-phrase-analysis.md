# 搜狗输入法「简写 → 短语」机制分析（REA 取证）

> 问题：**搜狗是怎么做到「输入几个字母，候选第一位就是那条短语」的？**
> 样本：Android 版搜狗输入法 `com.sohu.inputmethod.sogou`（真机 ALN-AL00 拉取，98,646,955 B）。
> 方法：REA 式**已发布制品取证** —— `resources.arsc` 字符串池 + `classes*.dex` 符号/字符串。
> 证据全部可复现，命令见 §7。**限制**：本机无 Ghidra/Hopper，未做反编译，结论来自
> 「文案 + 符号名」的静态证据（见 §8 诚实声明）。

---

## 0. 结论速览

| 维度 | 搜狗的做法 |
|---|---|
| 术语 | 「简写」在搜狗叫 **输入码**（input code）；= 你打的那几个字母 |
| 匹配 | 输入码作为**独立字段**存库，与内容、分组、位置并列 |
| **候选位次** | **不是算出来的，是用户显式填的字段** —— 「**输入码位置**」 |
| 输入码约束 | **仅小写字母**、**≤10 位**、必填、不可重复 |
| 内容约束 | 单个词条 **≤10 字**；词库导入时候选长度 1-20 |
| 条数上限 | 自定义短语 **300 条**；词库导入 **20 万组** |
| 排序 | 编码相同时 **按导入顺序**；跨编码时由「输入码位置」指定槽位 |
| 存储 | `custom_phrase_db`（greenDAO：`PhraseBeanDao` / `GroupPhraseBeanDao`） |
| 演进 | 新版把「快捷短语」与「自定义短语」**合并为「常用语」**，并支持云同步分组 |

**一句话**：搜狗把「排第几」做成了**用户可填的字段**，而不是像我们这样用权重 + 档位推导。

## 3. 证据：词库导入规范原文（8 条）

这是搜狗在「自定义五笔方案 / 词库导入」页给出的**完整格式规范**（`resources.arsc` 原文摘录）：

```
导入数据要求：
1、支持导入 TXT 格式的文本文件。
2、文件编码格式支持：ANSI、UTF-8、UTF-16 LE。
3、文件内数据格式要求：
 （1）每行包含 1 个编码及 1 个或多个候选，通过空格或 Tab 键分隔；
 （2）编码长度：1-4；候选长度：1-20；          ← 与我们的 MAX_CODE_LENGTH=4 完全一致
 （3）支持 Z 键作为五笔编码（需关闭【Z键作为五笔通配按键】…）；
 （4）注意：编码相同时，候选项排序依据导入时的顺序排列；   ← 排序规则：导入顺序
 （5）候选项仅支持中文字词；
 （6）不符合以上规则，会直接舍弃整行数据；
 （7）最多支持 20 万组（编码-候选对应为 1 组）数据；
 （8）符合规则的数据示例：
        fnhe 韬 敖
        gqty AAIS 戒酒 莱茵河 菊花酒 黄花岗 莲花山 蓬莱山
        aamm 8
```

两个要点：

1. **编码长度 1-4** —— 搜狗自己也把五笔侧编码卡在 4 位（与我们 `MAX_CODE_LENGTH = 4` 相同）。
   所以「输入码 ≤10 位」是**拼音侧**的能力：拼音缓冲区长（我们 `MAX_PINYIN_LENGTH = 12`），
   五笔缓冲区短（4）。同一套短语，**在五笔键盘上只有 ≤4 位的输入码打得出来**。
2. **编码相同时按导入顺序** —— 搜狗在「同码多候选」时不用权重，用**文件里的先后**。

## 4. 数据模型还原（据上述证据）

```
CustomPhrase {
    输入码        : String   // 仅小写字母，≤10 位，必填，全局唯一
    内容          : String   // ≤10 字（自定义短语）；词库导入时候选 1-20
    输入码位置     : Int      // 候选槽位（必填，有格式校验）  ← 关键
    分组          : Group    // CustomPhraseGroupModel
    目录          : String   // 「可更改输入码和目录」
}
上限：300 条 / 分组数量亦有上限（「分组数量已达到上限」）
存储：custom_phrase_db（greenDAO）
```

## 5. 与我们实现的对照

| 维度 | 搜狗 | iSpeech 现状 | 差距 |
|---|---|---|---|
| 简写字段名 | 输入码 | `trigger`（`quick_phrases.txt` 第 1 列） | 语义等价 |
| 字母约束 | 仅小写字母 | `^[a-z]+$`（`check_quick_trigger.py` 强制） | ✅ 一致 |
| 长度 | **≤10 位**（拼音侧）；五笔侧实际 ≤4 | 文档写 1-4；五笔缓冲区 4、拼音缓冲区 12 | ⚠️ 需明确「五笔态只能 ≤4」 |
| **候选位次** | **用户显式填「输入码位置」** | 由 `weight` + `LookupKind.order` **推导** | ❌ 关键差异 |
| 同码多候选排序 | **导入顺序** | 权重降序 → display 升序 | ⚠️ 不同模型 |
| 分组 | 有（且云同步） | 仅 内置/远端/用户 三类来源 | ⚠️ |
| 唯一性 | 有（「自定义短语已存在」） | 校验脚本查 `trigger` 唯一 | ✅ |
| 条数上限 | 300 | 无 | ⚠️ |
| 内容长度上限 | 10 字 | 无 | ⚠️ |
| 总开关 | 「启用自定义短语」 | 「启用快捷短语」 | ✅ |

**为什么我们「输入简写后短语排第一」仍然成立**：`LookupKind.order` 里 `QUICKAPPLY(0) < PHRASE(1) < WUBI(2)`，
且 `CandidateRanking` 对「精确命中触发码」再加一档优先级 —— 效果上等价于搜狗的「输入码位置 = 1」，
但**只对首位有效，无法表达「放在第 3 位」**。

## 6. 对本次需求（添加几个字母作为简写）的启示

1. **纯数据即可满足**：搜狗这套说明「简写 → 首位候选」不需要新机制，我们已有的
   `trigger` + 档位排序就能达成，与搜狗行为一致。
2. **值得借鉴的三点**（若要更像搜狗）：
   - **「候选位置」字段**：让用户说「这条放第 N 位」，而不是只能靠权重调；
   - **单条内容 ≤10 字 + 总条数上限**：防止一条超长文本误上屏、防止规则表失控；
   - **同码按导入顺序**：比权重更可预测（用户看得见文件里的先后）。
3. **必须澄清的一点**：**五笔态下输入码超过 4 位是打不出来的**（缓冲区 `MAX_CODE_LENGTH=4`，
   与搜狗规范「编码长度 1-4」一致）。所以简写建议 **1-4 位**；只有切到拼音态才可能用到更长。
   现有规则表里的 `slogan`（6 位）正是踩在这条线上（`check_quick_trigger.py` 已告警）。

```bash
cd work/sogou-android   # sogou.apk 所在目录

# 符号名证据（§1）
python3 -I -c "
import zipfile,re
z=zipfile.ZipFile('sogou.apk')
for d in [n for n in z.namelist() if re.match(r'classes\d*\.dex\$',n)]:
    t=z.read(d).decode('utf-8','ignore')
    for k in ['custom_phrase_db','phrasePosition','setInputCodeLengthFilter','CustomPhraseMatchCodeNetSwitch']:

"

# UI 文案证据（§2）：含「输入码 / 自定义短语」的完整串

import zipfile,re
raw=zipfile.ZipFile('sogou.apk').read('resources.arsc')
pat=re.compile(r'[一-鿿0-9A-Za-z（），。：；、？！“”…%\s]{4,60}')
seen=set()
for enc in ('utf-8','utf-16-le'):

print('\n'.join(sorted(seen)))
```

## 8. 诚实声明

- 本分析**未使用** REA 的 `decompile` / `search` / `analyze`（本机无 Ghidra/Hopper/IDA，这些命令
  一律 `provider_unavailable`）。结论来自 `resources.arsc` 字符串池与 `classes*.dex` 的
  **符号名 + 字符串**静态证据。
- **未验证**：`输入码位置` 的**取值范围**（1-9 还是 1-5）未从证据中确证，只知道它有格式校验
  （`输入码位置格式不正确`）；也未确证匹配是精确还是前缀。
- **未验证**：自定义短语在**五笔态**下的实际匹配行为（是只匹配 ≤4 位，还是拼音态才生效）——
  这需要真机 A/B 实测，属于「已发布制品的运行时行为」，静态证据无法覆盖。
- 上述两项属于**下一步可验证项**，不应作为已确认结论引用。
