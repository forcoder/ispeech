# Reverse Skill

复刻的目标不是「看起来像」，而是**行为等价且可被验证**。任何一条没有被观测记录支撑的结论都不要写进交付物。

## 何时适用

- 用户要求复刻 / 克隆 / 移植某个已有产品（App、桌面软件、网页、协议、外设）的功能
- 只有产物没有源码：APK、二进制、抓包、DOM、截图、导出文件
- 需要判断「某个功能能不能复刻」，以及复刻需要什么前提

## 工作流

1. **建立行为清单（先列后做）**：把目标功能拆成可观测行为，而不是名词。
   每条写成：`触发动作 → 可观测输出 → 边界条件 → 失败表现`。
   例：`输入 wqiy → 候选第 1 项为「你」→ 不足 4 码时追加前缀候选 → 无匹配时不弹候选`。
2. **为每条行为找证据**：静态（反编译、资源/字符串提取、文件格式）或动态（抓包、日志、UI 自动化、黄金样例采集）。
   证据要留下原始记录（截图、报文、日志片段、文件字节），**不能凭记忆或文档描述**。参见 [references/observation-toolbox.md](references/observation-toolbox.md)。
3. **先写验证再写实现**：把行为转成可执行的断言（脚本或测试），确认它在当前实现上失败、在目标产物上成立，再去实现。
4. **数据与算法分开**：数据类能力（词库、规则表、映射表）优先提取成独立数据文件随项目发布；算法类能力才写进代码。提取数据时记录来源与版本。
5. **逐条闭环**：每条行为都要有「已复刻 / 有差异 / 无法复刻」的状态与理由，差异必须写明具体表现而不是「大致相同」。

## 交付物

一份行为矩阵，可直接作为 README 或 docs 页：

| 功能 | 目标产物行为（证据来源） | 复刻状态 | 差异 | 验证方式 |
| --- | --- | --- | --- | --- |
| … | … | 已复刻 / 有差异 / 无法复刻 | 具体差异 | 脚本 / 手工步骤 |

再加一节「无法复刻项与前提」，写清缺什么（数据源、私有算法、系统权限、云端服务）就能做。

## 硬性约束

- **只复刻行为，不搬运资产**：商标、图标、皮肤、词库、字体等受版权保护的内容不要拷贝；需要等价能力时自建或使用许可明确的数据源。
- **不伪造证据**：取不到证据（无网络、无设备、无权限）就如实标注该行为「未观测」，不要用推测填空。
- **授权边界**：对第三方服务只做用户自己有权测试的观测；抓包 / 重放不要指向未授权的第三方系统。
- **避免过度声称**：没有真机或编译环境时，明确写「未编译 / 未实测」，不要写「已验证通过」。

## 反模式

- 先写实现再补行为清单 → 会漏掉边界与失败路径
- 把「文档写着支持」当成证据 → 文档与实现经常不一致
- 一次复刻一大批功能 → 断言粒度太大，失败时无法定位
