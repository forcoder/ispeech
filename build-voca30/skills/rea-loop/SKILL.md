# REA Loop（Reason → Act → Verify）

面向「一轮做不完」的任务：并行开发、大改造、跨模块重构。核心是把不可控的大动作拆成**可验证的小循环**，
每一轮都留下证据，任何一轮中断都能接着做。

## 何时适用

- 任务跨多个文件 / 多个模块，或要交给多个 agent 并行做
- 需要一边实现一边验证，而不是最后一次性「应该没问题」
- 需求里出现「复刻全部功能」「重构」「并行加速」这类没有天然终点的表述

## 循环结构

每一轮都走这四步，不要跳步：

1. **Reason（定契约）**：先冻结接口——函数签名、数据结构、回调名、文件边界。
   契约没冻结就并行，等于制造冲突。写下来（哪怕只是给 agent 的 prompt 里逐字列出）。
2. **Act（并行执行）**：按**独占写集**分工，一个文件只归一个执行者。
   关键路径（下一个动作依赖它的那件事）自己留着做，别派出去等。
3. **Verify（独立验证）**：验证者不能是实现者。没有编译器/真机时，用能跑的东西验证：
   静态一致性检查（资源引用、括号配平、跨文件符号）、数据与逻辑测试（把算法语义在可控环境里复现）、
   对抗式代码评审（专挑崩溃点、状态机冲突、边界）。
4. **Close（闭环）**：按影响面清单逐条核对——调用点、序列化格式、配置项、测试、文档、版本号是否都跟着改了；
   删掉因变更失效的孤儿代码与 import。

## 每轮固定记录（写进最终汇报，别省）

```
本轮目标：
冻结的契约：
执行者与写集：A: file1,file2 | B: file3（互不重叠）
验证方式与真实结果：命令 → 输出摘要（含 PASS/FAIL 计数与失败明细）
影响面清单与勾选状态：
未闭环项 + 原因（缺环境/缺数据/缺权限）：
下一轮唯一最高优先级的动作：
```

## 优先级规则

- 用户说「优先保证 X」时，X 就是关键路径：先把 X 做到可运行、可验证，再扩功能
- 边角功能宁可少做，也不要让主干处于「未验证」状态
- 失败优于含糊：报告「未编译 / 未实测 / 缺 3 个候选」比笼统写「已完成」有用得多

## 反模式

- 先并行再定接口 → 合并时全是冲突与不兼容签名
- 让实现者自证正确 → 验证不会有新信息
- 一轮改一大片、最后统一验证 → 失败点无法定位
- 任务没有验收标准就开始动工 → 永远做不完
